## Executive Summary

This branch adds a `/model-current` slash command that surfaces the effective AI configuration — default provider/model, reviewer slots, role overrides, and active review mode — while also wiring up auto-commit of dirty worktrees before `/review` and `/pr` runs. Three structural defects reached unanimous consensus across all reviewers: `buildReviewRunners` is called outside the try-catch in `handleReview`, leaving a deferred Discord interaction permanently hanging if `AdversarialReviewError` is thrown there; the ⚠️ display in `handleModelCurrent` uses `isProviderEnabled` (flag-only) while `/review` validation uses `getProviderUnavailableMessage` (flags plus credentials), so Gemini or OpenCode configured without their required API key/auth shows as usable in the display but is rejected at runtime; and `clear:true` via `/model-select` only nulls columns in `guild_review_config` while the non-slot runtime still falls back to the legacy `guild_model_config` override, making the clear semantically incomplete for migrated guilds. These defects collectively affect correctness, UX trust, and administrator control flow, which is why the verdict is revise.

## Blocking Issues

- `buildReviewRunners` called outside the try-catch block in `handleReview` (src/discord/bot.ts): After `interaction.deferReply()` and the auto-commit await succeed, `buildReviewRunners` is invoked before the try block begins. If it throws `AdversarialReviewError('INSUFFICIENT_REVIEWERS')` — reachable via a narrow race where slots are deleted between `validateReviewConfig` and the runner build — the exception propagates unhandled and the interaction remains deferred indefinitely, showing 'Bot is thinking…' with no resolution. All three reviewers confirmed this structural defect.
- `isProviderEnabled` used for ⚠️ display; `getProviderUnavailableMessage` used for actual validation — display misleads for Gemini/OpenCode without credentials (src/discord/bot.ts): `handleModelCurrent` appends ⚠️ *disabled by server* only when the feature flag is off (`isProviderEnabled`). `validateReviewConfig` additionally checks `geminiApiKey` and `hasOpencodeAuth()` via `getProviderUnavailableMessage`. With Gemini flag on and `GEMINI_API_KEY` unset, the display shows the provider as active with no warning, but `/review` blocks the user. The discrepancy is confirmed by direct code comparison across all reviewers.
- `clear:true` cannot clear effective reviewer-role overrides for migrated guilds (src/discord/bot.ts): `clearGuildReviewRoleConfig` nulls only the `guild_review_config` columns. In the non-slot runtime path, `resolveRoleRunner` falls through via `??` to the legacy `guild_model_config` value. A guild that migrated a Gemini override into `guild_review_config` and then runs `clear:true` will see the display cleared but the runtime still applies the Gemini legacy entry. All reviewers confirmed this gap.

## Non-Blocking Issues

- `hasRoleOverride` is dead code in the non-slot path (src/discord/bot.ts): The inner function is defined at `src/discord/bot.ts:2569–2571` but its result is never used. `resolveRoleRunner` re-implements the same check and is the only thing called. No behavioral defect, but maintenance risk and reader confusion. Confirmed by all three reviewers.
- Role resolution logic is duplicated across `validateReviewConfig`, `buildReviewRunners`, and `handleModelCurrent` (src/discord/bot.ts): All three locations independently implement `guild_review_config → guild_model_config → default ordering` with independent `isProviderEnabled` checks. Any one diverging silently is hard to catch. Confirmed by OpenCode and Claude; Codex corroborated.
- Summarizer fallback display is opaque in legacy mode (src/discord/bot.ts): The slot path shows exactly which slot the summarizer falls back to. The legacy path emits 'falls back to default reviewer ordering' without indicating whether that means `reviewers[1]` or `reviewers[0]`. Minor UX gap; confirmed by OpenCode and Claude.
- `setGuildReviewConfig` `options` parameter has no caller and no tests (src/db/database.ts): The new options overload allowing atomic role-provider updates alongside `rounds` is unreachable from any call site in this PR. The UPSERT logic looks correct but is entirely untested. Claude and OpenCode both flagged this.
- Legacy `guild_model_config` overrides silently reappear if slots are deleted — not documented (src/discord/bot.ts): When slots exist, legacy overrides are suppressed in both display and runtime. If an admin later deletes all slots, those legacy overrides reappear with no warning. The behavior is intentional but undocumented for users. Raised by Claude and Codex.

## Missing Tests

- No test for `/model-current` ⚠️ suffix when a `guild_review_config` override references a provider whose flag is off
- No test for `/model-current` with a provider whose flag is on but credentials are missing (e.g., Gemini enabled, `GEMINI_API_KEY` absent) — the ⚠️ never fires in this case
- No test for `clear:true` on a migrated guild to verify the effective runtime override is actually gone, not just the `guild_review_config` row
- No test for slot mode alongside legacy `guild_model_config` role overrides to document the intended precedence behavior
- No test for `setGuildReviewConfig` with partial `options` (e.g., setting `analyzerProvider` without touching `judgePrivilege`) to confirm non-targeted columns are preserved
- No test for non-slot `buildReviewRunners` with active `guild_review_config` role overrides — the runner-building path is exercised only via display-level model-current tests
- No migration test for a DB schema that has all optional audit columns present (`updated_by_user_id`, `created_at`, `updated_at`) in the legacy table

## Disputed Issues

- Whether slot mode suppressing `guild_model_config` legacy overrides is a design defect or intentional: Codex calls it a blocking hierarchy violation; OpenCode and Claude treat it as a deliberate replacement paradigm consistent with the commit message and code. No authoritative spec was cited by any party.
- Whether the auto-commit behavior added to `/review` and `/pr` is out-of-scope for a `/model-current` PR: Codex argues it inflates review surface; other reviewers accept it as a coherent architectural choice.

## Outstanding Concerns

- Codex's `clear:true` finding implies a broader migration-completeness gap: no path exists to definitively clear an effective legacy role override short of also nulling the `guild_model_config` row, which no slash command currently offers. The fix for the blocking `clear:true` issue should either extend the clear to touch `guild_model_config` or document and surface this limitation explicitly.
- The `isProviderEnabled` vs `getProviderUnavailableMessage` fix will require deciding whether `handleModelCurrent` should call the async credential checks on every invocation. Claude's suggestion — run credential checks only for providers that actually appear in configured slots or overrides — is the most practical middle ground and should be evaluated during the fix.
- The three-way duplication of role-resolution logic elevates the risk that a future change to the override hierarchy updates one site but not the others; a shared resolver function would be the safer long-term approach even if not strictly required for this PR.
