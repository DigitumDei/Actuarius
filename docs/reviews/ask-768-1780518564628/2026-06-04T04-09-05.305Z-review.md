## Executive Summary

This branch adds reviewer slot configuration, role overrides (analyzer/judge/summarizer), a migration from the legacy `reviewer_slots` table, and auto-commit of the dirty worktree before `/review` runs. Three reviewers converged on four blocking defects after two critique rounds: (1) clearing the last role override unconditionally deletes the `guild_review_config` row, silently destroying any separately-configured `rounds` value; (2) setting a role override on a guild with no prior review config row inserts `rounds = 1`, silently downgrading from the documented default of 2 rounds; (3) the new auto-commit step can commit `docs/reviews/**` artifact files that are subsequently excluded from the reviewed diff, allowing those commits to pass `/pr`'s reviewed-SHA check without ever being reviewed; (4) `/model-current` computes the summarizer fallback as the first slot differing from slot 1 by value, while `buildReviewRunners` always uses slot 2 by position, so the display and runtime diverge for any three-or-more-slot configuration where slots 1 and 2 are identical. The verdict is revise because all four issues are observable from static analysis, two involve silent data loss, and one creates a review-integrity bypass.

## Blocking Issues

- `clearGuildReviewRoleConfig` deletes entire `guild_review_config` row, discarding `rounds` (src/db/database.ts): When the last role-provider column is NULLed out, the method unconditionally DELETEs the row without checking whether `rounds` was explicitly set. A guild that ran `/review-rounds 5` and then cleared all reviewer overrides silently loses its round limit with no warning or recovery path.
- `setGuildReviewRoleConfig` inserts `rounds = 1` for guilds with no prior review config row (src/db/database.ts): The INSERT on line 894 hardcodes `VALUES (?, 1, ?, ?, ?)`. On a fresh guild, any `/reviewer-*` command creates the config row with `rounds = 1`, silently changing the effective round count from the documented default of 2 to 1. The companion test asserts `rounds === 1`, codifying the regression rather than catching it.
- Auto-commit before `/review` can push unreviewed `docs/reviews/**` artifacts through the reviewed-SHA gate (src/discord/bot.ts): A first `/review` run writes artifact files under `docs/reviews/` but does not commit them. A subsequent `/review` auto-commits the dirty worktree (including those artifacts) via `git add -A` with no path exclusion. The review diff then excludes `docs/reviews/**`, so the artifact commit is never reviewed. `/pr` compares HEAD against the `diff_head` recorded by the latest review, which already includes the artifact commit, so the SHA check passes and the unreviewed files are pushed.
- Summarizer fallback logic in `/model-current` disagrees with `buildReviewRunners` at runtime (src/discord/bot.ts): The display path finds the summarizer fallback as the first slot whose provider or model differs from slot 1. The runtime path always uses `reviewers[1] ?? reviewers[0]` (slot 2 by array position). With slots `[claude, claude, gemini]`, the display shows slot 3 (Gemini) while the runner uses slot 2 (Claude), giving users false configuration information.

## Non-Blocking Issues

- Slot mode weakens adversarial review guarantee (src/discord/bot.ts): Legacy mode required at least two enabled providers with distinct identities; slot mode only requires two slot entries, even if both resolve to the same provider and model. Tests explicitly bless identical claude/claude slots. This is a material reduction in reviewer independence, whether intentional or not.
- Legacy `modelConfig` role overrides shown in `/model-current` but silently ignored at runtime in slot mode (src/discord/bot.ts): `handleModelCurrent` reads role overrides from `guild_model_config` unconditionally, so legacy overrides appear in the display. `buildReviewRunners` in slot mode only reads `guild_review_config` and ignores `modelConfig` role overrides entirely. Users see configuration that has no runtime effect.
- `validateReviewConfig` checks only feature-enable flags, not credential availability (src/discord/bot.ts): If a server loses a required credential (e.g. `GEMINI_API_KEY`) after a provider was enabled, `/review` passes preflight validation and fails deep in execution with a non-actionable error instead of failing fast with the credential-check message that `getProviderUnavailableMessage` would produce.
- `setGuildReviewRoleModelConfig` is dead code with a hardcoded `'claude'` default (src/db/database.ts): The method is public and tested but has no caller in `bot.ts`. Its INSERT hardcodes `provider = 'claude'`, so any future wiring would silently set Claude as the default for that guild row regardless of actual server configuration.

## Missing Tests

- Preserve `rounds` across `clearGuildReviewRoleConfig`: set a round limit, set a role override, clear the override, assert `rounds` survives — this scenario currently confirms the data-loss bug rather than preventing it
- Repeated-review path with pre-existing `docs/reviews/` artifacts in the worktree: verify that artifact files from a prior review run are not silently committed and excluded from the subsequent review diff
- Three-slot heterogeneous configuration (e.g. `[claude, claude, gemini]`): assert that `/model-current` display and `buildReviewRunners` runtime agree on the summarizer fallback slot
- Stale provider credentials at review time: enable a provider via feature flag, remove its required credential, assert `/review` fails at preflight with an actionable message rather than deep in execution

## Disputed Issues

- `reviewConfig!` non-null assertions in `buildReviewRunners` slot mode: OpenCode flagged as blocking; Claude and Codex disagreed, noting the assertions are only reached inside `hasSlotOverride(role)` branches where the object is guaranteed non-null by the same synchronous guard. Downgraded to not blocking.
- SQLite migration crash-recovery for `INSERT OR IGNORE` + `DROP TABLE reviewer_slots`: OpenCode raised a scenario where a crash between INSERT and DROP loses rows on retry; Claude correctly noted that SQLite transaction semantics roll back the entire transaction on crash, making the concern moot. Concern dismissed.

## Outstanding Concerns

- The `rounds = 1` insert bug and the clear-deletion bug compound silently: a guild that sets a role override gets `rounds = 1` inserted; if that override is later cleared, the row is deleted and rounds reverts to the display default of 2. The guild's effective round count oscillates between 1 and 2 solely based on whether any role override is active, with no visible signal to admins.
- Several tests assert the newly-introduced incorrect behavior (e.g. `rounds === 1` after a role override, identical reviewer slots) rather than protecting the intended behavior, meaning the test suite cannot serve as a regression guard for the blocking fixes.
