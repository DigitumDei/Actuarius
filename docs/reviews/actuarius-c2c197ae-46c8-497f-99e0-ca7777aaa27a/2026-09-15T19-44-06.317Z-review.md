## Executive Summary

This branch migrates Actuarius from the deprecated Gemini CLI to Google's Antigravity CLI while preserving Gemini configuration compatibility, authentication modes, MCP settings, and related documentation. The implementation's core runtime and MCP changes are generally coherent, but the official installer currently rejects the supplied flags and exits successfully without updating an existing binary, leaving fresh deployments without agy and making update reporting misleading. A smaller output-parsing defect can misinterpret protocol-shaped lines in plain-text responses, so the branch requires revision.

## Blocking Issues

- Official installer rejects the supplied flags (docker/seed-provider-clis.sh): The installer currently accepts only --dir and --help, so --skip-aliases and --skip-path cause installation to exit before downloading agy. Both fresh container seeding and /update-clis are affected.
- Installer does not update existing agy binaries (src/services/antigravityCli.ts): When the target binary already exists, the official installer exits successfully without replacing or updating it. The seed process and /update-clis can therefore report success while retaining an old version, contrary to the branch's stated update behavior.

## Non-Blocking Issues

- Plain-text output can be misread as structured protocol: Stream parsing and result-failure detection are applied to plain-text output as well as structured output. A response containing an NDJSON-shaped result line can be incorrectly replaced or marked failed; parsing should be gated on the structured transport.
- Activity summaries omit terminal result status (src/utils/runProviderRequest.ts): The generic result-event branch returns before the code that appends result.status, so error-path activity summaries report only the event name.

## Missing Tests

- Use a pinned fixture or contract test for the real installer argument parser, including fresh installation, existing-binary behavior, and failed-update preservation.
- Add tests proving plain-text NDJSON-shaped lines are preserved and structured streams without a terminal result are handled correctly.
- Add coverage for empty SUCCESS responses, download failures, and WAITING/RUNNING result statuses.
- Exercise at least one realistic agy invocation or equivalent pinned contract fixture for prompt transport, authentication behavior, stream output, and MCP configuration.

## Disputed Issues

- The plain-text protocol-parsing defect is accepted as real, but reviewers differed on whether its likelihood warrants blocking severity; consensus treats it as non-blocking.
- The loss of credential preflight feedback for Gemini was viewed by one reviewer as a UX regression, while another considered it compatible with account authentication and not an established defect.

## Outstanding Concerns

- The Antigravity installer URL is mutable and its served script conflicts with the documented flags, so the claimed verified contract is not durable without a pinned fixture or versioned installer strategy.
- Live agy installation, execution, authentication, and deployment behavior remain unverified; current tests rely heavily on mocks that cannot detect the installer failures.

# Review: R1 — Actuarius Antigravity CLI (agy) migration

## Blocking Issues

**B1. `--skip-aliases` / `--skip-path` are rejected by the actual official installer — agy is never installed in production.**
Everything in this change hinges on Google's installer contract, so I downloaded `https://antigravity.google/cli/install.sh` (the exact `AGY_INSTALL_URL` used by `seed-provider-clis.sh`, `antigravityCli.ts`, and the README). Its argument parser is:

```bash
while [ "$#" -gt 0 ]; do
    case $1 in
        -d|--dir) ... ;;
        -h|--help) ... ;;
        *) echo "[ERROR] Unknown parameter: $1" >&2; show_usage; exit 1 ;;
    esac
done
```

Only `-d/--dir` and `-h/--help` are handled. `bash "$installer" --skip-aliases --skip-path` exits 1 before any download. Consequences:
- `install_agy()` in `docker/seed-provider-clis.sh:61,68` fails on both attempts every boot → agy missing → gemini provider broken (`GEMINI_UNAVAILABLE`) on every fresh container.
- `installOrUpdateAgy()` in `src/services/antigravityCli.ts:135` (used by `/update-clis`) always throws.
- The README's manual update `bash -s -- --skip-aliases --skip-path` (base commit docs, line ~273) fails the same way.

The docs pages *claim* these flags exist, but the script actually served at the pinned URL does not implement them. A prior reviewer in this same round (codex diary, `agy-round-1-review`) independently reproduced "official installer rejecting `--skip-aliases`". This is a verified, deployment-breaking mismatch. The seed script must be reconciled with the real (currently byte-served) installer — e.g. omit the unsupported flags, or detect/blackriver version skew and fail loudly instead of silently producing no agy.
Repro: `curl -fsSL https://antigravity.google/cli/install.sh -o /tmp/i.sh; bash /tmp/i.sh --skip-aliases --skip-path` → `[ERROR] Unknown parameter: --skip-aliases`.

**B2. Even with the flags removed, the installer will not update agy, contradicting the stated seeding intent.**
The same installer contains an early-exit pre-existence check (top of STEP 2):
```
if [ -f "$BINARY_PATH" ]; then
    echo "Notice: 'agy' is already installed at $BINARY_PATH."
    echo "The Antigravity CLI automatically self-updates in the background ..."
    echo "If you want to perform a fresh installation, delete the binary first:  rm \"$BINARY_PATH\""
    exit 0
fi
```
So the seed script's headline rationale ("So we always install the latest of each package on startup; a restart then picks up upstream releases", `docker/seed-provider-clis.sh:10-12`) is false for agy: re-running the installer on a volume that already has `~/.local/bin/agy` is a silent no-op (exit 0). `/update-clis` will report "Updated Antigravity to latest" without updating anything, and a rebuilt image will never deliver a newer agy. The retry-once logic and the "removing partial install" messaging in `install_agy` also don't do anything useful against this installer. This needs either a "delete the binary then reinstall" strategy, an explicit version check, or a documented acceptance that only agy's background self-update ever changes the binary; right now the code documents a behavior it cannot deliver.

## Non-Blocking Issues

**N1. The provider-unavailable UX gate for gemini became weaker.** `getProviderUnavailableMessage` and `handleModelSelect` no longer reject gemini without credentials, and the auth hint only surfaces at runtime. A guild that previously got the friendly "Gemini execution requires `GEMINI_API_KEY`" on selection now passes `/model-select gemini`, and `/ask` fails only later with `NOT_AUTHENTICATED`/`FAILED`. This matches the account-auth intent, but it's a real regression in pre-flight feedback (the old message was removed wholesale).

**N2. Auth-detection regex is broad and stdout is deliberately ignored.** `authFailurePattern` includes `modelProvider` and `authentication required`, tested only against stderr (`authCheckOnlyStderr: true`). Docs do put diagnostics on stderr, so this is likely correct, but `modelProvider` is a substring that could appear in benign diagnostic text. Low risk, worth a narrower pattern.

**N3. `ensureAntigravityApiKeyConfig` is racy under concurrent `/ask`.** Multiple gemini requests (concurrency defaults bump this) can interleave `readFile`→merge→`writeFile` on the settings JSON. Writes are idempotent for consistent env, so transiently both write the same content; a mixed key/no-key interleaving could briefly leave `modelProvider` set while a keyless agy starts — agy refuses to start in that state. Practically benign (all requests share process env) but the function does an unbounded read-modify-write per request with no lock/atomic write.

**N4. README's manual update instruction contradicts nothing but is wrong for the same flag reason** as B1; also the manual example pipes the installer (`curl … | bash -s --`), which the seed script's own comment explicitly argues against ("never piped"). Docs and script disagree with each other.

**N5. Verification script still couples to the dead legacy file** — `scripts/verify-agentpalace-http.mjs` and `agentPalaceHttpConfig.ts` keep writing/checking `.gemini/settings.json` (the retired Gemini CLI's file) alongside the new `mcp_config.json`. Harmless, but it's now documented as legacy; the extra write to settings.json on every converge is dead IO.

**N6. `detectAntigravityResultFailure` maps `WAITING` and `RUNNING` to failure.** Docs define these as "ended while waiting on input" / "did not reach a terminal state". For the single-prompt-close-stdin flow these shouldn't appear, but a race where the process exits before the turn's result (see docs "waiting for process exit" caveat) could convert a legitimately readable response into `FAILED`. Acceptable conservatism, but the distinction wasn't reasoned through in the code.

**N7. Small-prompt stream output double-parsing risk.** `extractAntigravityStreamResponse`/`detectAntigravityResultFailure` are applied to *all* stdout including the plain-text argv path; a multi-line text response containing one valid NDJSON-looking line `{"event":"result",...}` would be misread. Astronomically unlikely for CLI output but the functions can't distinguish transports. Low priority.

## Missing Tests

**M1. (Actionable) Seed-installer contract is not tested at all.** The `seedProviderClis.test.ts` curl mock emits an *empty* installer (`: > "$out"`), so `bash <empty> --skip-aliases --skip-path` is a no-op success and the test would pass even though the real installer rejects the flags — exactly the failure in B1/B2. There is no test asserting the installer is invoked with flags the real script supports, and no fixture reproducing the real installer's arg parsing / pre-existence exit. This is the single most important test gap.

**M2. No live/consultative agy invocation test.** Every execution path is a spawn mock. The contract claims — `-p` text, `--dangerously-skip-permissions`, stream-json result shape, `modelProvider` behavior, MCP file location — are asserted against hand-written fixtures only. Given B1/B2 just disproved a documented contract, at least one golden test against real agy (or a pinned real-installer fixture) is warranted. Current status is "unverified, assumed".

**M3. No test for `installOrUpdateAgy` curl-failure temp-dir cleanup** (there is one for installer non-zero exit, none for the download step failing).

**M4. No test for `EMPTY_OUTPUT` on a SUCCESS stream whose `response` is empty**, nor for the plain-text argv path where the response contains NDJSON-shaped lines (N7).

**M5. `detectAntigravityResultFailure` WAITING/RUNNING thresholds have no targeted tests**, only `ERROR`/`CANCELED`/`INTERRUPTED`.

## Strong Concerns

**S1. Deployment of this branch will likely ship without agy.** B1 is reproducible against the live installer right now and was independently reproduced by the codex reviewer in this round. Unless the installer was updated between checks, a fresh container never obtains agy; the test suite green-lights this because of M1. This is the strongest confidence-destroying finding in the change.

**S2. `installOrUpdateAgy` and shell `install_agy` duplicate installer logic and now diverge** (TS: no retry, no "preserve existing" handling; shell: retry-once, asserts atomic-replace semantics the real installer doesn't have). Both are wrong against the real installer today.

**S3. The `.env.example`/README guidance "Do not set the key without the marker, or the marker without the key" is correct, and the runtime marker merge handles it** — this portion is solid. The settings-merge logic (`ensureAntigravityApiKeyConfig` preserving unrelated keys, malformed-file empathy, marker removal for account auth) is well-reasoned and well-tested.

**S4. The MCP registration change is correct against the docs.** The new agy global file `~/.gemini/config/mcp_config.json` with `serverUrl` for remote servers matches the authoritative MCP page ("`serverUrl` field; legacy `url`/`httpUrl` not supported"), and unrelated servers are preserved (only `mempalace`/`agentpalace` keys mutated) — this satisfies the "maintains MCP settings without overwriting unrelated servers" criterion.

## Confidence

Medium. The MCP/auth/settings-streaming code is coherent, well-commented, and matches the *documented* Antigravity contract; targeted tests for it are good. But the two highest-value claims of the change — the install flags and the "always latest on startup" semantics — are **disproven against the installer actually served at the pinned URL**, and the tests that cover them use a mock that cannot catch either defect. Until agy is exercised for real (install, `-p` run, API-key vs account auth, `/update-clis`), I would not merge.
