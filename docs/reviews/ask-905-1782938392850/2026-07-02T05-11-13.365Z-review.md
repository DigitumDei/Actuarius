## Executive Summary

This branch implements issue #152 by surfacing partial stdout/stderr and worktree state (recent commits, git status, unstaged diff) when a provider times out during /ask, /plan, or /revise execution. The plumbing from spawnCollect through runProviderRequest into the four provider error classes and buildTimeoutReport is mechanically correct, and tsc --noEmit passes cleanly. However, the most user-visible artifact of the change — the timeout report — is assembled from untrusted, user-influenceable CLI output and pushed to Discord without mention-token neutralization or code fencing, creating a ping-injection vector in a Discord bot context. Combined with zero test coverage across the entire new surface area, the branch is not safe to merge as-is.

## Blocking Issues

- Mention injection via raw partial output and commit subjects (src/discord/bot.ts): partialStdout, partialStderr, and commit subject lines are pushed as raw Discord content (bot.ts:4199, 4205, 4217) with no code fence and no allowedMentions override. The Discord Client is constructed without a global allowedMentions (bot.ts:472-475) and no per-send override is passed to threadChannel.send(). User/role mention tokens (<@userId>, <@&roleId>) in captured CLI output ping unconditionally regardless of bot permissions; @everyone/@here ping if Mention Everyone is granted. Because /ask prompts are user-controlled and provider CLIs routinely echo them to stdout, this is an exploitable abuse vector. The completed-output path already fences its content (bot.ts:150-183); shipping the timeout path without equivalent protection is a regression in safety posture. Fix: wrap partial output in code fences and/or set allowedMentions: { parse: [] } on timeout-report sends.

## Non-Blocking Issues

- splitPlainTextForDiscord is markdown-unaware and can split fenced blocks mid-fence (src/discord/bot.ts): The splitter (bot.ts:263-303) splits on lastIndexOf('\n', maxLength) with no awareness of code-fence boundaries. The timeout report emits ``` and ```diff fenced sections; a report exceeding 2000 chars can be cut mid-fence, leaving an unclosed fence in one message and an orphan closer in the next. Severity is borderline: each section is pre-clipped to 1800 chars, so the split must land across a section boundary — real but not universal. Disputed whether this independently blocks.
- Dead (unavailable) catch branches in buildTimeoutReport (src/services/gitWorkspaceService.ts): All four new git helpers (gitWorkspaceService.ts:639-685) swallow every error internally via catch { return ''/[] }, so the try/catch wrappers in buildTimeoutReport (bot.ts:4210-4249) can never throw. The '(unavailable)' push branches are unreachable dead code, and a genuine git inspection failure is indistinguishable from a clean/empty worktree — the report silently shows nothing instead of signaling failure.
- Large-diff overflow fallback is defeated by runGitDiffWithOverflowFallback (src/services/gitWorkspaceService.ts): runGitDiffWithOverflowFallback returns clipOverflowedDiff(stdout) on EMSGSIZE rather than throwing, so getUnstagedDiffSummary's --stat/--name-only fallback chain is unreachable on overflow. buildTimeoutReport then clips the prefix to 1800 chars, yielding the beginning of one file rather than a useful changed-file summary.
- Over-broad 'timed out' substring detection mislabels unrelated errors (src/discord/bot.ts): The final isTimeout clause at bot.ts:4185 matches any Error whose message contains 'timed out', potentially relabeling non-timeout provider or git errors and triggering the worktree report. Degrades gracefully; the typed code === 'TIMEOUT' checks above it are the reliable path.
- Staged-but-uncommitted changes have no diff shown (src/services/gitWorkspaceService.ts): getUnstagedDiffSummary runs bare git diff (working-tree vs index). Agentic CLIs frequently run git add before timing out; staged content appears in git status --short by letter but its diff hunks are absent from the report. git diff HEAD or a separate --cached section would be more complete.
- Silent-timeout heading degrades to 'execution failed' rather than 'execution timed out' (src/discord/bot.ts): When a genuine TIMEOUT produces no partial output and a clean worktree, buildTimeoutReport returns '' (falsy), all three callers' if (timeoutReport) branches fail, and the else branch sends the generic 'execution failed' heading. However, describeExecutionError returns error.message, which contains 'timed out after Nms', so the message body still explicitly identifies the timeout. Only the bold heading and enhanced worktree report are lost. Non-blocking because issue #152's 'clear timeout notice' criterion is minimally satisfied via the body.
