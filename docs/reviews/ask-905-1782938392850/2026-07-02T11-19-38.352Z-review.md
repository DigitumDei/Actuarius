## Executive Summary

This branch improves timeout reporting in the Discord bot by detecting provider timeouts reliably, capturing partial stdout/stderr from timed-out runs, summarizing workspace state (staged and unstaged changes), and splitting long Discord messages without breaking code fences. All three reviewers independently reproduced a merge-blocking regression in the new fence-aware split logic: `splitPlainTextForDiscord` misclassifies closing fences as unclosed openers because `afterOpen = remaining.slice(fenceStart + 1, splitAt)` starts at the backticks, making the closing-fence regex `/\n```\s*(?:\n|$)/` structurally unable to match the fence that was just located — so every closing fence is treated as an unclosed opener and the split retreats into the block, producing unbalanced fence markers across chunks that are worse than the pre-change naive split. Beyond this confirmed regression, the branch carries no tests for any of the new behavior, and several feature-completeness gaps remain against its own stated success criteria, warranting revision before merge.

## Blocking Issues

- Fence-aware split produces malformed Discord output — regression vs. pre-change behavior (src/discord/bot.ts): All three reviewers independently reproduced this on realistic input (a closed fenced block followed by trailing text, total exceeding 2000 chars). `lastIndexOf("\n```", splitAt)` returns the nearest fence marker, which is a closing fence when the split point falls after a completed block. Because `afterOpen` starts at the backticks rather than before them, the closer-regex requiring a leading `\n` can never match the located fence, so every closer is misclassified as an unclosed opener and `splitAt` retreats — splitting blocks that fit in one message and emitting chunks with unbalanced markers. Pre-change code produced balanced chunks for the same input. A fence at offset zero (no leading `\n`) is also invisible to the pattern. No tests cover this logic, and no tests were added with this change.

## Non-Blocking Issues

- Global `allowedMentions: { parse: [] }` on the Client constructor suppresses all bot mention pings, not just timeout-report sends (src/discord/bot.ts): The three per-send `allowedMentions` guards on timeout chunks already accomplish the stated goal of suppressing mentions on timeout sends. Setting it at the `Client` level makes it the default for every message the bot sends, silently suppressing intentional `<@userId>` pings at multiple existing send sites (install completion/failure notices, request attribution). The Client-level line should be dropped; the per-send guards are sufficient.
- Detached-worktree timeouts lose all workspace state (status, staged diffs, unstaged diffs) (src/discord/bot.ts): `buildTimeoutReport` gates all git inspection on `worktreePath && branchName`. The `/bug` and `/issue` commands set `detachWorktree: true`, which propagates to `createRequestWorktree({ detached: true })` and returns `branchName: null`. A timed-out `/bug` or `/issue` run therefore silently skips status, unstaged diffs, and staged diffs — none of which conceptually require a branch name. The fix is to gate diffs and status on `worktreePath` alone and gate only the commits section on `branchName`.
- Large-but-under-buffer diffs are head-sliced rather than summarized with file/stat information (src/services/gitWorkspaceService.ts): The `--stat`/`--name-only` fallback fires only on `EMSGSIZE` (>4MB maxBuffer). Any diff between ~1800 chars and 4MB is returned in full by `getUnstagedDiffSummary`/`getStagedDiffSummary` and then blindly head-sliced by `clipForDiscord(diff, 1800)`, discarding the changed-file overview the PR explicitly intends to preserve. The codebase already has `runGitDiffWithOverflowFallback`/`clipOverflowedDiff` implementing the cleaner size-based fallback; the new helpers diverge from that established pattern.
- `--stat` failure aborts the fallback chain before `--name-only` is attempted (src/services/gitWorkspaceService.ts): In `getUnstagedDiffSummary` and `getStagedDiffSummary`, both `--stat` and `--name-only` share a single inner `try` block. If `git diff --stat` itself throws, the `catch` returns `""` immediately and `--name-only` is never attempted, making the two-level fallback effectively one-level.
- Silent git-helper failures are indistinguishable from a clean workspace (src/services/gitWorkspaceService.ts): `getCommitsSinceBaseRef`, `getShortStatus`, and `getDefaultBranchBaseRef` swallow all errors to `[]`/`""`. A missing `origin/main` ref, a stale checkout, or any git failure silently produces an empty result, giving users no indication whether the workspace was actually clean or the inspection failed.
- Dead guard in `buildTimeoutReport` (src/discord/bot.ts): The `if (!this.isProviderTimeout(error)) return ""` check inside `buildTimeoutReport` is unreachable — all three call sites already gate on `isProviderTimeout` before invoking the method. Harmless as defensive code, but should be removed for clarity.

## Missing Tests

- `buildTimeoutReport`: clean-worktree fallback content, staged+unstaged section assembly, detached (`branchName: null`) path producing a partial but valid report

## Disputed Issues

- Auth-before-timeout ordering (runProviderRequest.ts ~line 212 vs ~line 229): All reviewers agree the auth-failure pattern check runs before the definitive ETIMEDOUT/SIGTERM check, and that a Gemini timeout whose partial output contains an authentication phrase is thrown as NOT_AUTHENTICATED — suppressing the entire timeout report. Codex classifies this as blocking; Claude and OpenCode note it is pre-existing on main (the branch only adds `details` propagation, not the ordering) and call it in-scope to fix now without calling it a regression this PR owns. No consensus on whether it must block this PR or can be a follow-up.

## Outstanding Concerns

- Unfenced partial output compounds the fence-split regression: `buildTimeoutReport` injects `clipForDiscord(partialStdout, 1800)` raw — without wrapping in a fenced block — and the assembled report then flows through `splitPlainTextForDiscord`. Agent stdout very commonly contains its own fences; an incomplete fence in partial output will corrupt Discord rendering independently of the splitter bug, and together they are the primary realistic failure path. A correct fix must either wrap/escape partial output before splitting or re-fence across chunk boundaries after splitting; the parity-based opener fix alone is insufficient.
- `splitPlainTextForDiscord` is a shared utility used by callers beyond the timeout-reporting path (issue details, summaries, plans). The fence-splitting regression affects any caller that produces output containing code fences, making the scope of the breakage broader than timeout reporting alone.
