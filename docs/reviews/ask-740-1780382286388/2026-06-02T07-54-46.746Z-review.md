## Executive Summary

This branch completes the adversarial review progress pipeline by adding `analyzer-start`/`analyzer-complete` events, wiring all progress event types to Discord messages in `handleReview`, and ensuring `onProgress` callbacks are properly awaited with failures surfaced as `PIPELINE_FAILED`. All three reviewers agreed the implementation is functionally correct — types check, 78/78 tests pass, event ordering is sound on all exit paths — but two operational fragility issues drew multi-reviewer consensus: progress callback failures (including Discord rate limits) abort the entire review, and a *hanging* callback (gateway stall rather than hard rejection) can stall the review pipeline indefinitely because `totalTimeoutMs` guards inter-stage budget checks but does not wrap the `onProgress` await itself. No reviewer identified a correctness defect or data-loss risk, so the verdict is ready for PR with the non-blocking findings tracked as follow-up.

## Non-Blocking Issues

- Hanging progress callback stalls the pipeline indefinitely (src/services/adversarialReviewService.ts): The `emitProgress` helper awaits `input.onProgress?.(event)` between `checkBudget()` calls. If the callback hangs rather than rejects (e.g., a Discord gateway stall on `reviewThread.send()`), no budget check fires during the hang and the review loop blocks forever — there is no timeout wrapping the callback, no `Promise.race`, no `AbortSignal`. `totalTimeoutMs` only covers inter-stage budget comparisons. A thrown rejection fails fast; a silent hang occupies the concurrency slot indefinitely.
- Any Discord `send()` failure in `onProgress` aborts the entire review as PIPELINE_FAILED (src/discord/bot.ts): A transient rate limit or dropped thread mid-review causes `reviewThread.send()` to throw, which propagates through `emitProgress`, is caught by the outer handler, and records the review as failed — discarding all token spend up to that point. This is intentional per the stated success criterion ('surface callback failures correctly') and is covered by a test, but the failure mode is operationally surprising: a non-critical status-update failure terminates work rather than degrading gracefully.
- Missing `summarizer-complete` event leaves a dangling 'Synthesizing…' spinner on failure (src/services/adversarialReviewService.ts): `summarizer-start` is emitted before the summarizer runs, but there is no `summarizer-complete` or `summarizer-failed` counterpart. If the summarizer times out or errors after emitting `summarizer-start`, the caller's last visible progress state is 'Synthesizing final verdict…' with no resolution. The review is still recorded as failed in the database, so this is a UX gap rather than a data-integrity issue.

## Missing Tests

- `maxConsensusRounds` exhaustion without consensus: the for-loop exiting naturally on the final round with `consensusReached: false`, then proceeding to `summarizer-start` — distinct from the all-critiques-fail `break` path and currently untested
- Discord `send()` failure propagating through `handleReview`'s `new Promise((resolve, reject))` wrapper and its catch block to a failed interaction reply — the service-level rejection test covers the isolation behavior but not the bot-layer integration path
- `runAdversarialReview` invoked without an `onProgress` callback: the optional-chaining no-op in `emitProgress` (`input.onProgress?.(event)`) is untested since both modified tests pass a callback

## Disputed Issues

- Test brittleness on `progressMarkers` mutable shared state: OpenCode argued the analyzer mock assertion (`expect(progressMarkers).toContain('awaited:analyzer-start')`) would become a race condition if `emitProgress` stopped awaiting callbacks; Codex and Claude's critique considered the failure mode mischaracterized — the assertion lives inside the callback itself and would fail loudly, not silently, if the await were removed
- `round-complete` metadata asymmetry on all-critiques-fail path: OpenCode flagged that the normal judge path and the all-critiques-fail hardcoded path produce structurally different `round-complete` payloads; Codex contested that the event type never carries `judgeDecision` metadata on either path, making this a non-issue in the current schema

## Outstanding Concerns

- The unbounded await on `onProgress` is the most operationally dangerous design point in this change. Unlike a thrown rejection (which fails fast and is tested), a callback that never resolves silently holds a concurrency slot for the lifetime of the Discord gateway stall. If this bot is used with long-running reviews, a single stalled Discord connection could exhaust the guild's concurrency limit. Wrapping the callback with a deadline (e.g., `Promise.race([callback, timeout])`) or documenting the assumption that callbacks will not hang would close this gap.
