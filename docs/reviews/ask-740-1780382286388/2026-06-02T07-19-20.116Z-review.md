## Executive Summary

This branch implements Discord progress reporting for `analyzer-start` and `analyzer-complete` events in the adversarial review pipeline, completing the last missing pieces of the progress-event surface. All three reviewers converged on a single blocking defect: `onProgress` is typed `(event: ReviewProgressEvent) => void` but the bot passes an async callback that awaits `interaction.channel.send()`; the service discards the returned Promise at every emission site, making all Discord progress sends fire-and-forget — producing unhandled rejections on send failures and non-deterministic message ordering. The bug is invisible to the type checker (TypeScript legally permits async-to-void assignment) and uncatchable by the existing test suite, which passes no `onProgress` spy in any `runAdversarialReview` call. The verdict is `revise`: the async/void contract mismatch is a demonstrable production hazard that must be fixed before merge.

## Changed Files

- src/discord/bot.ts

## Blocking Issues

- onProgress typed void but called with async Discord callback — Promises silently dropped (src/services/adversarialReviewService.ts): adversarialReviewService.ts:620 declares onProgress as (event: ReviewProgressEvent) => void. The bot passes an async callback that awaits interaction.channel.send(). TypeScript does not flag this assignment. At runtime, every input.onProgress?.({...}) call discards the returned Promise: send failures become unhandled rejections and Discord messages can arrive out of order relative to later events or the final summary. Fix requires typing the callback as (event: ReviewProgressEvent) => Promise<void> | void and awaiting each call site in the service.

## Non-Blocking Issues

- round-complete not emitted when all critiques fail (src/services/adversarialReviewService.ts): When activeReviewers.length === 0 after critique failures the loop breaks before the round-complete emission, but round-start already fired for that round. Users see a round start with no matching completion before 'Synthesizing final verdict…' appears.
- analyzer-complete not emitted on analyzer failure (src/services/adversarialReviewService.ts): analyzer-start fires before analyzer.run(), but if run() throws, analyzer-complete is never reached. Users see 'Analyzing change intent…' followed by an error with no signal that the analysis phase itself ended.
- No summarizer-complete event — asymmetry with other stage pairs (src/services/adversarialReviewService.ts): summarizer-start is emitted but has no matching completion event, unlike analyzer-start/analyzer-complete and round-start/round-complete. Minor UX inconsistency; the final result message implicitly closes the phase but the asymmetry in the event API is worth addressing.

## Missing Tests

- adversarialReviewService.test.ts: no test passes an onProgress spy to runAdversarialReview — all new event-emission code paths have zero coverage
- adversarialReviewService.test.ts: no test verifies event ordering (analyzer-start → analyzer-complete → round-start → round-complete × N → summarizer-start)
- adversarialReviewService.test.ts: no test verifies round-complete is omitted (while round-start was emitted) when all critiques fail
- adversarialReviewService.test.ts: no test verifies analyzer-complete is not emitted when analyzer.run() throws
- bot command test: no test proves handleReview passes onProgress to runAdversarialReview and that analyzer-start/complete events produce the expected Discord message strings
- bot command test: using an async onProgress spy that returns a rejected Promise would immediately expose the fire-and-forget bug — this test is absent

## Disputed Issues

- Whether missing round-complete (on all-critique-failure path) is blocking or non-blocking: OpenCode classified it blocking; Codex and Claude treated it as a non-blocking event-contract consistency gap.
- Whether per-call-site try/catch around onProgress is required (OpenCode) vs. the existing outer try/catch at the pipeline boundary being sufficient: reviewers disagreed on whether coarse-grained isolation is adequate for graceful progress-send degradation.

## Outstanding Concerns

- If interaction.channel.send() rejects mid-review (channel deleted, thread archived, Discord rate limit), the rejected Promise is silently dropped under the current fire-and-forget design with no logger.warn — making progress-send failures completely invisible in production logs regardless of which fix is applied to the async contract.

### OpenCode (opencode / deepseek/deepseek-v4-pro)

```text
## Blocking Issues

**1. Unhandled promise rejections from progress callbacks**

The `onProgress` callback type in `adversarialReviewService.ts:620` declares `(event: ReviewProgressEvent) => void`, but the bot passes an `async` function that returns `Promise<void>`. The service calls `onProgress` without `await` at every call site (`input.onProgress?.({ ... })`). If any `interaction.channel.send()` inside the callback rejects (network errors, rate limits, etc.), the resulting Promise rejection has no `.catch()` handler — an unhandled rejection. In environments running with `--unhandled-rejections=strict`, this crashes the process. At minimum, progress messages are silently lost, defeating the purpose of this change.

**2. Missing `round-complete` event when all critiques fail**

At `adversarialReviewService.ts:813-818`, when `activeReviewers.length === 0` after critique failures, the loop `break`s before the judge runs and before `round-complete` fires at line 843. But `round-start` already fired for that round at line 688. This leaves the progress state inconsistent — the user sees a round start but never sees it complete, then suddenly sees "Synthesizing final verdict…" with no explanation.

**3. No error isolation around progress callbacks**

If the `onProgress` callback throws synchronously (e.g., a property access on an unexpected event shape), the error propagates directly into the review pipeline with no try/catch, aborting the entire review. Each `onProgress` call site should be wrapped in a try/catch so progress-reporting failures can't kill the review.

## Non-Blocking Issues

**1. Missing `analyzer-complete` on analyzer failure**

`analyzer-start` fires at line 666, then `input.analyzer.run()` at line 672 can throw. The `analyzer-complete` at line 678 is never reached. Users see "Analyzing change intent…" followed eventually by a failure message with no indication that analysis itself failed.

**2. Type signature is misleading**

`onProgress?: (event: ReviewProgressEvent) => void` at line 620 implies a synchronous callback, but the real consumer is async. The type should be `Promise<void> | void` to honestly declare that it may return a promise.

**3. No `summarizer-complete` or completion event**

Every other stage has a start/complete pair (`analyzer-start`/`analyzer-complete`, `round-start`/`round-complete`), but `summarizer-start` has no matching completion event. The end of summarization is implicitly signaled by the final result message, but the asymmetry is worth noting.

## Missing Tests

**1. Zero test coverage for the entire progress-reporting pipeline**

No test file references `onProgress`, `analyzer-start`, `analyzer-complete`, `round-start`, `round-complete`, or `summarizer-start`. Tests that should exist:
- `adversarialReviewService.test.ts`: Verify each event fires at the correct pipeline stage.
- `adversarialReviewService.test.ts`: Verify `onProgress` is not called when omitted.
- `botCommands.test.ts`: Verify the callback maps each `ReviewProgressEvent` variant to the expected Discord message string.
- `botCommands.test.ts`: Verify `onProgress` is included in the `runAdversarialReview` call at all (the existing `maxConsensusRounds` test at line 1325 should be extended).

## Strong Concerns

**1. Progress messages fail silently with no logging**

If `interaction.channel.send` fails mid-review (e.g., `analyzer-start` succeeds but `round-start` throws), the review continues with the user receiving a partial or broken progress stream and no logged warning. There should be at least a `logger.warn` on failures.

**2. Out-of-order delivery risk**

Because `onProgress` is fire-and-forget (not awaited), multiple calls can race. For example, `analyzer-start` and `analyzer-complete` are called sequentially without awaiting the first, so the Discord messages could arrive in either order depending on network timing. While practically unlikely for two messages in quick succession, it's an architectural weakness.

## Confidence

**Medium-Low.** The event type definitions are well-structured, and the wiring in `bot.ts` cleanly maps events to messages. But the untested, fire-and-forget async pattern with no error handling is fragile in production — Discord API calls fail regularly, and the entire progress-reporting surface has zero test coverage to catch regressions in event ordering or the round-complete omission path.
```
