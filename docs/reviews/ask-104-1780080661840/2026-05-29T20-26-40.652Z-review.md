## Executive Summary

The branch adds Discord attachment support to Actuarius: `/ask` accepts optional attachments and thread follow-ups (including attachment-only ones) trigger a fallback prompt, with attachments validated for count/size/type, downloaded into `.actuarius/attachments/request-<id>/`, git-ignored even in linked worktrees (via the common `info/exclude`), and surfaced to the provider as text excerpts or image paths; follow-up history reconstruction preserves prior attachment summaries. Reviewers reached consensus that the core flow is correct and well-tested — validation, download-time size re-checking, linked-worktree exclusion (backed by a real-`git` integration test), and history dedup all hold up under tracing. The round-1 attachment-only `/ask` blocker was retracted once the source criteria (review doc lines 75-76) were quoted: they scope attachment-only behavior to thread follow-ups and only require `/ask` to accept *optional* attachments, so the feature meets the stated intent. The verdict is ready_for_pr because no consensus blocking issue survives; the remaining items are hardening, documentation, and test-coverage refinements.

## Non-Blocking Issues

- Attachment download has no timeout/AbortSignal (src/services/attachmentService.ts): processAttachments issues a bare `await fetch(att.url)` before provider execution, so `askExecutionTimeoutMs` (which wraps only the AI run) doesn't cover it. A stalled Discord CDN connection holds one of the per-guild queue slots (default concurrency 3) indefinitely with no recovery. All reviewers agree this is the single most worthwhile fix (a few-line `AbortSignal.timeout(...)`); two of three rate it non-blocking and the critique consensus agrees.
- Hardcoded 5 attachment slots vs configurable ATTACHMENT_MAX_COUNT (src/discord/commands.ts): commands.ts registers exactly attachment1–5 and handleAsk loops `i=1..5`, independent of `attachmentMaxCount`. Raising the config above 5 silently caps the slash UI at 5; lowering it is still enforced by validateAttachments but only after submission (worse UX). Discord's static option schema makes a fully dynamic count awkward, so a shared constant tied to the config plus a comment is the pragmatic fix.
- New ATTACHMENT_* env vars are undocumented (src/config.ts): ATTACHMENT_MAX_COUNT, ATTACHMENT_MAX_FILE_SIZE, ATTACHMENT_MAX_TOTAL_SIZE, and ATTACHMENT_MAX_INLINE_TEXT are defined in config.ts but appear in none of .env.example, README.md, docs/deploy.md, or CLAUDE.md's env list. Operators get defaults silently with no deployment guidance.
- arrayBuffer() buffers the full response before the size check (src/services/attachmentService.ts): Post-download per-file/total size enforcement runs after the entire body is materialized via arrayBuffer(), so a response larger than the advertised att.size spikes memory before rejection. Bounded in practice by the metadata pre-check and default caps (~35 MiB worst case), so minor, but the guard doesn't bound peak memory.
- Inline-text clipping compares character count against a byte budget (src/services/attachmentService.ts): maxInlineText is a byte value (default 262144, formatted as bytes) but clipping uses textContent.length (UTF-16 code units) and .slice, so multibyte content can exceed the intended byte cap. Cosmetic since it's a soft guard, but the unit mismatch is real.
- Duplicate .toml and .yaml entries in TEXT_EXTENSIONS (src/services/attachmentService.ts): Both extensions are listed twice. Harmless because the values land in a Set, but sloppy.
- pendingAttachmentsFromMessage helper duplicated inline in handleThreadMessage (src/discord/bot.ts): The PendingAttachment mapping at bot.ts:528-534 is identical to the helper at bot.ts:348-357, which is otherwise unused on that path. Reuse the helper or inline it consistently.
- Non-atomic ensureActuariusExcluded read-check-append (src/services/attachmentService.ts): Two concurrent calls writing the same worktree's common info/exclude can both see the entry missing and append `.actuarius/` twice. Git tolerates duplicate exclude lines and each request normally gets its own worktree, so functionally harmless.
- Mis-cased mempalace fields in test fixture (tests/botCommands.test.ts): tests/botCommands.test.ts:110-112 sets memPalaceEnabled/memPalacePalacePath/memPalaceBinaryPath while the real config keys are lowercase-p (mempalaceEnabled, etc.). Harmless today (tests aren't in the tsc include set and the field resolves undefined → disabled), but the fixture silently doesn't configure what it appears to.
- Stale Discord CDN URLs at execution time (src/discord/bot.ts): Downloads use att.url at execution time, but Discord attachment URLs are signed and expire (~24h). For a long-queued or reused-worktree follow-up the fetch can 403 and fail the whole request. Re-fetching message attachment metadata at execution time would yield a fresh URL. Latent, not a normal-path failure.
- Exact-match MIME sets miss parameterized content types (src/services/attachmentService.ts): IMAGE_MIMES.has(lower)/TEXT_LIKE_MIMES.has(lower) won't match e.g. `application/json; charset=utf-8`; the extension fallback usually rescues it. Narrow but real edge case.
- Partial files left on mid-batch failure (src/services/attachmentService.ts): If attachment N fails the post-download size check, attachments 1..N-1 are already written under .actuarius/. They're git-ignored and the worktree is cleaned eventually, so nothing leaks into commits, but cleanup-on-failure is unspecified.
