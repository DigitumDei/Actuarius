## Executive Summary

The branch implements Discord attachment support (issue 88): users can attach files to `/ask` commands and follow-up thread messages, which are validated (count/size/type), downloaded into the request worktree, and surfaced to the AI prompt as text excerpts or image-file references. Reviewers reached consensus that the core flow is well-structured and error handling is sound, but uncovered one operationally significant defect — uploaded attachments are written inside the git worktree (`.actuarius/attachments/...`) with no gitignore/exclude, so the bot's own `git add`/commit/PR workflow can silently leak user files into their repo history — plus several genuine but lower-severity gaps (unenforced downloaded byte size, over-broad `image/*` MIME acceptance, hardcoded 5-attachment cap, UTF-16-vs-byte clipping drift) and thin test coverage of the primary `/ask` attachment-to-prompt path. The verdict is `revise` because the worktree-leak finding is an unresolved, high-consequence blocking issue acknowledged as valid by all three reviewers.

## Blocking Issues

- Attachments are written inside the git worktree with no gitignore/exclude, risking commit into user repos (src/services/attachmentService.ts): processAttachments saves downloads to `.actuarius/attachments/request-<id>/` inside the request worktree, which is the repo checkout. No `.gitignore` or `.git/info/exclude` entry for `.actuarius` exists anywhere in the service layer (confirmed by all three reviewers). Since the bot's purpose is to have the AI commit changes and open PRs, a broad `git add -A` will silently stage users' uploaded files (including binary images) into the branch and resulting PR — a hard-to-undo data-handling side effect on user repositories. Fix by excluding `.actuarius/` via the worktree's `.git/info/exclude` at creation, or storing attachments outside the checkout and passing absolute paths.

## Non-Blocking Issues

- Downloaded response bytes are never enforced against maxFileSize/maxTotalSize (src/services/attachmentService.ts): processAttachments fetches the URL and calls arrayBuffer() then writes the buffer, trusting the Discord-reported `att.size` that validation saw. A stale, redirected, or oversized response is written to disk and inlined without bound. Note maxCount and per-file size ARE enforced upstream in validateAttachments at command time; the genuine gap is the actual downloaded byte count, not count enforcement.
- detectType accepts any image/* MIME, broader than the supported PNG/JPEG/WebP/GIF set (src/services/attachmentService.ts): `lower.startsWith("image/")` waves through image/svg+xml, HEIC, TIFF, etc. before the extension-based fallback, while the validation error message advertises only four formats. OpenCode noted the practical window is narrower (manifests mainly when an unsupported image/* MIME is paired with a supported/forged extension, since MIME is preferred over extension), but it remains a real type-validation/intent mismatch.
- /ask hardcodes exactly five attachment options, decoupled from ATTACHMENT_MAX_COUNT (src/discord/bot.ts): commands.ts declares five fixed attachmentN options and bot.ts loops 1..5, while ATTACHMENT_MAX_COUNT is configurable. Configuring above 5 leaves extra capacity unreachable via the slash command; configuring below 5 exposes more UI options than allowed and triggers a validation error after selection. Follow-up messages honor the config since they read message.attachments. The magic 5 is duplicated across three sites.
- Inline-text clipping uses UTF-16 code units, not bytes (src/services/attachmentService.ts): textContent.length and .slice() count UTF-16 code units against ATTACHMENT_MAX_INLINE_TEXT, which reads as a byte budget, so multibyte content overshoots the configured cap and the clipped-notice message (formatFileSize) misreports the size. Reviewers agreed the real corruption risk is limited to surrogate-pair splitting (astral chars/emoji), not general non-ASCII text, and that naive byte-slicing as a fix can itself emit U+FFFD.
- Prompt summary reports att.size rather than saved buffer length (src/services/attachmentService.ts): The prompt and clipping note use the Discord-reported size, so if metadata diverges from the actual downloaded bytes the reported sizes are misleading. Ties into the unenforced-byte-count gap.
- No download timeout on attachment fetch inside the queue worker (src/services/attachmentService.ts): The bare `await fetch(att.url)` has no AbortSignal/timeout and runs inside runQueuedRequest before provider execution, so a stalled CDN request can occupy a queue slot independent of askExecutionTimeoutMs. A simple AbortSignal.timeout would address it.
- Discord CDN signed URLs may expire between enqueue and download (src/discord/bot.ts): The attachment URL is captured at command time but fetched later inside the bounded queue, widening the window for an opaque HTTP 403/404 download failure under queue latency.
- No cleanup of already-saved attachments on partial download failure (src/services/attachmentService.ts): If a later attachment in a batch fails, previously saved files remain on disk in the worktree. Intersects with the worktree-leak issue.
- Unused import formatFileSize in bot.ts (src/discord/bot.ts): formatFileSize is imported but never referenced in bot.ts; passes tsc only because noUnusedLocals is off. Should be removed.

## Missing Tests

- buildThreadPromptWithHistory dedup/append logic: attachment-only fallback prompt path and the guard preventing double-appending a normal text follow-up (the subtlest part of the diff, verified only by manual trace)
- Integration test that processAttachments' promptSection actually reaches the effective prompt in runQueuedRequest
- End-to-end /ask slash path through handleAsk with real attachments (download, save, seed-message Attachments summary)
- Assertion that attachment files are excluded from git (ties to the blocking worktree-leak issue)
- Response body larger than declared attachment size / configured limits (oversized download)
- Unsupported image/* MIME values such as image/svg+xml
- /ask behavior when ATTACHMENT_MAX_COUNT differs from 5 (both above and below)
- Non-ASCII / surrogate-pair text inline clipping and the maxInlineText byte-vs-code-unit boundary
- Direct tests for buildAttachmentSummary and multi/mixed-type attachment processing in processAttachments

## Disputed Issues

- Severity of the unenforced downloaded-byte-size gap: Codex rated it blocking (unbounded memory/disk), Claude and OpenCode rated it non-blocking given Discord metadata is generally trustworthy
- Severity of the over-broad image/* MIME acceptance: Codex rated it blocking; Claude and OpenCode rated it non-blocking, with OpenCode arguing the exploit window is narrow (requires contradictory MIME/extension)
- Severity of the UTF-16-vs-byte inline-clipping drift: OpenCode rated it blocking with a claimed corruption mechanism; Codex and Claude judged the corruption claim overstated (limited to surrogate pairs) and the issue cosmetic/non-blocking, and flagged OpenCode's proposed byte-slice fix as itself UTF-8-unsafe
- OpenCode characterized the buildThreadPromptWithHistory change as an unrelated/sneaked-in fix; Codex and Claude refuted this, showing it is load-bearing for the attachment-only follow-up fallback (and noted OpenCode misnamed the function as formatRequestHistory)

## Outstanding Concerns

- The worktree-leak blocking severity is conditional on the AI choosing broad staging (e.g. git add -A); reviewers recommend quoting the actual staging instruction given to the model to fully substantiate the risk, but agree the fix (per-worktree exclude or out-of-checkout storage) is cheap and warranted regardless
- The validate-at-command-time-then-re-derive-type-but-not-size-at-download split is a design smell likely to drift; a single re-validation against the same AttachmentConfig inside processAttachments would be safer and nearly free
- Follow-up attachment contents are appended only to the provider prompt, not posted into thread history, so later follow-ups may lose concrete attachment context
