## Executive Summary

The branch implements Discord attachment support (issue #88/#104) for Actuarius: `/ask` and thread follow-ups accept attachments that are validated (count/size/total/MIME), downloaded, stored under git-ignored `.actuarius/attachments/request-<id>/` in the request worktree, and surfaced to the AI prompt as inlined text excerpts or image path references. It also lands follow-up safety fixes including a verified linked-worktree git-ignore fix (resolving the common git dir and writing to its shared `info/exclude`, exercised against a real `git worktree`), post-download actual-size enforcement, and unsupported-image-MIME rejection. The reviewers reached consensus that the core pipeline and the headline ignore fix are sound, but that follow-up attachment metadata is not persisted into durable thread history: attachment-only follow-up turns vanish from later `buildThreadPromptWithHistory` reconstructions and text-plus-attachment follow-ups lose their attachment summary. The verdict is `revise` because that durable-history gap is an unresolved consensus blocking issue, alongside several non-blocking robustness and coverage gaps.

## Blocking Issues

- Follow-up attachment metadata is not persisted into durable thread history (src/discord/bot.ts): handleThreadMessage posts no seed/summary message for follow-ups, so attachment context lives only in the ephemeral effectivePrompt. parseThreadEntry returns null for empty-content messages, so an attachment-only follow-up turn disappears entirely from any future buildThreadPromptWithHistory reconstruction; text-plus-attachment follow-ups retain only the text and lose the attachment summary. The current request still receives attachment context — the loss surfaces on subsequent follow-ups. All three reviewers validated this in critique (Claude revised its initial no-blocker stance).

## Non-Blocking Issues

- `/ask` hard-codes five attachment slots while ATTACHMENT_MAX_COUNT is configurable (src/discord/commands.ts): commands.ts defines exactly attachment1..5 and the handler loops 1..5, so raising ATTACHMENT_MAX_COUNT cannot increase slash-command capacity. Likely constrained by Discord's command-option shape, but the config should then be capped/documented or framed as a follow-up-only limit, and the loop keyed off a shared constant rather than duplicated across two files.
- New attachment env vars are undocumented (src/config.ts): No ATTACHMENT_* entries exist in .env.example, README.md, or deploy docs, so operators cannot discover the defaults or limits without reading source.
- Response is fully buffered via arrayBuffer() before the actual-size check, and there is no download timeout (src/services/attachmentService.ts): validateAttachments caps the declared Discord size before fetch, but a lying/redirected response can still spend memory up to its actual size before rejection. Separately, fetch(att.url) has no AbortSignal/timeout, so a stalled CDN download can hold a queue slot indefinitely (ASK_EXECUTION_TIMEOUT_MS covers only the AI run). Severity is bounded by the pre-download metadata guard.
- Concurrent appends to the shared info/exclude can race (src/services/attachmentService.ts): ensureActuariusExcluded does read → check → appendFile against the common git dir shared by all linked worktrees of a repo. With same-guild ASK_CONCURRENCY_PER_GUILD (default 3), two requests on the same repo can both observe 'no entry' and both append, producing a duplicate line. Harmless to git but the test only covers sequential calls.
- Content-type with parameters bypasses the MIME allow-list (src/services/attachmentService.ts): detectType uses exact Set.has(lower) for TEXT_LIKE_MIMES/IMAGE_MIMES, so a real header like 'application/json; charset=utf-8' fails to match and falls through to the extension check. Mostly rescued by extension fallback, but the MIME matching is more brittle than the bare-MIME-string tests suggest.
- History dedup only checks the last thread entry (src/discord/bot.ts): buildThreadPromptWithHistory compares only the last history entry against the new message, so two messages fired in quick succession can cause an earlier message to be appended twice. Low impact (mildly redundant prompt context), not a correctness failure.
- Image support is path-reference only (src/services/attachmentService.ts): Images are saved and referenced as 'Attached image: <relpath>'; no image bytes are passed to the provider. This works for the Claude CLI (file-reading tools) but non-file-reading providers may never see the image. Matches the literal success criterion but the usefulness is provider-dependent and undocumented.
- Test config uses wrong mempalace key casing (tests/botCommands.test.ts): tests/botCommands.test.ts uses memPalaceEnabled/memPalacePalacePath/memPalaceBinaryPath while appConfig exports the lowercase mempalace* keys, so these test values are silently ignored (tests aren't type-checked). Misleading; orthogonal to attachments.
- Minor cosmetic items: no aggregate inline-text cap, formatFileSize lacks GiB, duplicate TEXT_EXTENSIONS entries (src/services/attachmentService.ts): maxInlineText is per-file only (~5×256 KiB ≈ 1.25 MB aggregate, bounded but uncapped); formatFileSize displays >=1 GiB as '1024.0 MiB'; .toml and .yaml appear twice in TEXT_EXTENSIONS (Set dedupes, no functional impact).

## Missing Tests

- Follow-up attachment propagation to runQueuedRequest end-to-end (the follow-up tests never invoke the enqueued thunk, so the followUpInput.attachments wiring and existing-worktree processAttachments path are unverified)
- The next follow-up after an attachment-only follow-up — that buildThreadPromptWithHistory preserves the prior attachment turn/summary
- Text-plus-attachment follow-up preserving the attachment summary in history
- /ask validation-error path (oversized/unsupported attachment → ephemeral reply, no createRequest)
- Multiple slash attachments (attachment1..5 mapping) at the bot layer
- Zero-byte text attachment handling in processAttachments
- Non-linked (regular) git repo path in ensureActuariusExcluded (the '.git is a file pointing to commondir' path)

## Disputed Issues

- Orphaned files on partial download failure: OpenCode labeled it blocking, but Codex and Claude downgraded it to minor housekeeping since the partial files live inside the already-retained, git-excluded worktree and are not an incremental leak beyond existing worktree retention.
- OpenCode's stale-closure-reference concern: dismissed by consensus as hypothetical (pendingAttachments is a const built once and never reassigned), not a present bug.
- OpenCode's 'dead dedup for attachment-only follow-ups' framing: rejected — no seed message containing the fallback string is ever created; the real issue is missing persistence of attachment summaries, not a regex/representation mismatch.
- OpenCode's cross-guild exclude-race scenario: invalid under the one-instance-per-guild deployment model; the real race is same-guild concurrency.

## Outstanding Concerns

- The 'blocking' label on the durable-history gap rests on issue #104's stated requirement, which is not present in the working tree; it should be confirmed against the PR/issue whether this is a requirement violation (blocking) or a documented known limitation, though the reviewers treat it as the primary actionable defect either way.
- Prompt injection via verbatim-inlined attachment text is inherent and unmitigated; worth an explicit acknowledgment given the agent runs with repo write access.
- Partial-failure cleanup in processAttachments has no dedicated test and no removal path, even though the leak is considered non-blocking.

### OpenCode (opencode / deepseek/deepseek-v4-flash)

```text
# Blocking Issues

1. **`processAttachments` writes files on disk mid-loop with no cleanup on partial failure.** If a multi-attachment download fails after some files have already been written (e.g., the 3rd of 5 files exceeds the actual-size limit), the earlier files remain on disk under `.actuarius/attachments/request-<id>/` and are never cleaned up. An orphaned directory is left behind. This is a leak that accumulates on failed requests.

2. **`handleThreadMessage` passes `pendingAttachments` to the queue closure, but the closure captures a stale reference if validation re-maps the array.** This is not actually a bug in the current code (the array is built once, validated, and captured), but it's fragile: any future refactor that re-assigns `pendingAttachments` after the queue closure is created (e.g., filtering out some entries) would silently break the captured reference. The closure at `bot.ts:536` should capture a shallow copy (`[...pendingAttachments]`) to be defensive.

# Non-Blocking Issues

1. **`formatFileSize` doesn't handle GiB+.** Values ≥ 1 GiB are displayed as `1024.0 MiB`. Cosmetic, but the config defaults use 10 MiB and 25 MiB so it's unlikely to trigger in practice.

2. **`TEXT_EXTENSIONS` contains duplicate entries.** `.toml` appears on lines 51 and 55 of `attachmentService.ts`; `.yaml` appears on lines 49 and 56. No functional impact.

3. **Hard-coded loop `for (let i = 1; i <= 5; i++)` in `handleAsk` is tightly coupled to the command definition.** Adding a 6th attachment option requires changes in two files. Should be keyed off the command options or a shared constant.

4. **`ensureActuariusExcluded` is called on every `processAttachments` invocation.** It reads and re-parses the exclude file each time. Idempotent but wasteful on the second+ request sharing the same repo. The `hasEntry` check prevents duplicate writes, though.

5. **Empty `.git/info/exclude` file gets `.actuarius/\n` prepended correctly, but no test validates the exact content for the initial write.** The test at `tests/attachmentService.test.ts:206` checks `toContain` and a regex, which is sufficient but not byte-exact.

# Missing Tests

1. **No test for the `handleAsk` validation-failure path.** When `validateAttachments` returns an error in `handleAsk`, the bot calls `interaction.reply({ content: error, ephemeral: true })` and returns. There is no test that exercises this branch.

2. **No test for `formatFileSize(0)` or values in the GiB range.** The function returns `"0 B"` and `"1024.0 MiB"` respectively; neither path is covered.

3. **No test for zero-byte text attachment in `processAttachments`.** A 0-length download succeeds, writes an empty file, produces an empty code fence in the prompt section, and `inlineContent` is `""`. This path is exercised only implicitly if at all.

4. **No test for a regular (non-linked) git repo path in `ensureActuariusExcluded`.** The unit test at `tests/attachmentService.test.ts:192` creates a fake `.git/` directory manually. The linked-worktree test at line 211 is the only integration-style test. The "`.git` is a file pointing to a non-worktree common dir" path is untested.

5. **No test that `processAttachments` cleans up on partial failure.** See Blocking Issue 1 — the cleanup gap is not tested.

# Strong Concerns

1. **The dedup check in `buildThreadPromptWithHistory` uses a raw string comparison (`lastEntry.text !== newMessageContent.trim()`).** This compares the *parsed* history text against the *raw* new-message text. Because `parseThreadEntry` extracts user text by `<regex>.exec(content)`, the parsed text may differ subtly from the raw prompt (regex boundaries, whitespace normalization). The dedup will fail to match across these representation differences, so the "no duplicate" guarantee is weaker than it appears. In practice the fallback prompt `"Please inspect the attached file(s)."` is unlikely to collide with parsed history entries (seed messages include extra markdown like `**Attachments**`), so the risk is low, but the comparison is not semantically robust — a seed message from a prior attachment-only request would contain `"Please inspect the attached file(s).\n\n**Attachments**\n..."` which would *not* match `"Please inspect the attached file(s)."`, causing the fallback to be appended every time.

2. **`processAttachments` re-validates and re-downloads attachments on every `runQueuedRequest` invocation, including follow-ups.** For initial requests this is correct. For follow-ups, the files were already downloaded and saved in the previous request's directory (`request-<prevId>`). The follow-up downloads them again and saves them under `request-<newId>`. This is intentional (each request has its own snapshot), but it doubles bandwidth usage on follow-ups with the same attachments. The intent says "downloads and stores them in the request worktree" so this is by design, but it's worth noting that downstream of an attachment-only follow-up there is no mechanism to reference previously-stored files.

3. **`ensureActuariusExcluded` resolves the common git directory and writes to its `info/exclude`, but the write is not atomic.** If multiple requests execute concurrently (e.g., in different guilds sharing the same main repo), both can read the exclude file, find no `.actuarius/` entry, and both append it. The result is a duplicate line, which is harmless (git ignores duplicate exclude lines) but produces a messy file. A lock or atomic-write-then-rename would eliminate this.

# Confidence

**Moderate.** The core attachment pipeline (validation → download → save → inject into prompt) is sound, the git-exclude logic correctly handles linked worktrees, and the tests cover the primary integration paths. The blocking issues are real but not severe — the orphaned-file leak accumulates slowly and the captured-reference concern is theoretical for now. The strongest concern is the `buildThreadPromptWithHistory` dedup comparison, which does not work for the one scenario it was presumably added for (attachment-only follow-ups) because the parsed history text includes the attachment summary suffix, guaranteeing a mismatch. This means attachment-only follow-ups always re-append their fallback text, making the dedup logic effectively dead for that case.
```
