## Executive Summary

The branch implements Discord attachment support for Actuarius: it adds optional attachments to `/ask` and thread follow-ups, validates count/size/type, downloads files into a request-scoped `.actuarius/attachments/` directory in the worktree, inlines supported text excerpts and passes image references into the AI prompt, and attempts to exclude saved attachments from git tracking. All three reviewers converged on one release-blocking defect: the git-exclusion writes `.actuarius/` to the per-worktree gitdir's `info/exclude`, which Git does not consult for linked worktrees (the kind `git worktree add` produces in production), so saved attachments remain visible to `git status` and can be committed into the PR branch. Codex and Claude both reproduced this against real Git (2.47.3), and OpenCode upgraded its initial 'no blocking issues' verdict to agree in critique. The verdict is `revise` because this core safety guarantee is broken and the existing test only asserts the exclude file was written, not that Git honors it.

## Blocking Issues

- Attachment git-exclusion is ineffective for linked worktrees (src/services/attachmentService.ts): `ensureActuariusExcluded` uses `resolveGitDir`, which for a linked worktree (`.git` is a file with a `gitdir:` line) returns the per-worktree gitdir and writes `.actuarius/` to its `info/exclude`. Git reads `info/exclude` only from the common git dir, so for production worktrees created by `git worktree add` the attachments are NOT excluded and `git status` still shows `?? .actuarius/...`. Reproduced independently by two reviewers on git 2.47.3. The recommended fix is to resolve the `commondir` file in the per-worktree gitdir and write to `<commondir>/info/exclude` (which collapses to the gitdir itself for a standalone `.git` directory, preserving the standalone case).

## Non-Blocking Issues

- Slash-command attachment count hardcoded at 5, decoupled from ATTACHMENT_MAX_COUNT (src/discord/commands.ts): `commands.ts` registers exactly 5 attachment options and `handleAsk` loops i=1..5, but `ATTACHMENT_MAX_COUNT` is configurable. Raising the config above 5 makes the extra capacity unreachable via `/ask` while thread follow-ups can exceed it; lowering it leaves dead options. Latent under the default of 5. The loop bound should derive from config and the slash cap documented.
- .env.example omits the four new attachment configuration knobs (.env.example): The change adds ATTACHMENT_MAX_COUNT, ATTACHMENT_MAX_FILE_SIZE, ATTACHMENT_MAX_TOTAL_SIZE, and ATTACHMENT_MAX_INLINE_TEXT to config.ts but none are documented in .env.example, forcing operators to read source to find defaults/overrides.
- processAttachments reads entire response into memory before enforcing byte limits (src/services/attachmentService.ts): `response.arrayBuffer()` fully buffers the body before the downloaded-size check. Metadata size is pre-validated, so this only bites when a CDN returns more than the declared size, but it offers no process-memory protection against an unexpectedly large response. Low severity.
- No download timeout on fetch() (src/services/attachmentService.ts): `fetch(att.url)` has no AbortController/timeout, so a hung or slow Discord CDN response can block attachment processing indefinitely.
- Config mock uses wrong key casing in botCommands.test.ts (tests/botCommands.test.ts): The test config uses memPalaceEnabled/memPalacePalacePath/memPalaceBinaryPath while the real config keys are mempalaceEnabled/mempalacePalacePath/mempalaceBinaryPath. The mock only passes because these paths aren't exercised and it is `as const`-cast; this is dead/misnamed config drift.
- Duplicate entries in TEXT_EXTENSIONS (src/services/attachmentService.ts): `.toml` and `.yaml` each appear twice. Deduplicated by Set at runtime so harmless, but sloppy.
- Dedup compares trimmed content but appends untrimmed value (src/discord/bot.ts): `buildThreadPromptWithHistory` compares `lastEntry.text !== newMessageContent.trim()` but pushes the untrimmed `newMessageContent`. Leading/trailing whitespace can defeat the dedup check and leak untrimmed text into the prompt. Minor.
- Attachment summary only posted on slash /ask seed message, not thread follow-ups: `buildAttachmentSummary` output is posted to the seed message for slash `/ask` but not for thread follow-up messages, a minor UX inconsistency.
- Discord CDN attachment URLs are time-limited signed URLs (src/services/attachmentService.ts): URLs are captured at interaction time and used later during queue processing; a backlogged queue could hit HTTP 401/403 expiry. Error handling is clear but the user loses the attachment and must retry. Consider capturing closer to download time or adding retry.

## Missing Tests

- Real Git integration test using `git worktree add` that asserts `.actuarius/` is actually ignored (via `git check-ignore` or `git status --untracked-files=all`) rather than only asserting the info/exclude file contents — this is the decisive test that would have caught the blocking bug.
- Coverage for ATTACHMENT_MAX_COUNT values other than 5 (e.g. >5 attachments on a thread follow-up; <5 on the slash path).
- Assertion that processed attachment files actually land on disk under the request-scoped directory with expected content, not just that the prompt path string is present.
- Zero-byte attachment handling.
- Filename collision after sanitization (relying on the index prefix to differentiate).
- Attachment-only follow-up composed with promptTransformer skipping.

## Disputed Issues

- OpenCode's 'race condition on shared info/exclude' — refuted by Codex and Claude for the current code, since each worktree targets a distinct per-worktree gitdir so the state is not shared today; the race only materializes after the blocking bug is fixed to target the common dir, where it produces at most a harmless duplicate line.
- Image attachments passed only as a path reference for non-Claude providers — Claude raised this; OpenCode (and Codex) consider it speculative since all providers execute with cwd=worktreePath, making the relative path valid; better framed as an outstanding concern than a defect.
- Prompt-injection / binary-as-text / fence-breakout concerns (OpenCode) — acknowledged as technically real but severity disputed; the content already feeds an AI agent operating on arbitrary repo contents, so reviewers judged it a cosmetic formatting issue rather than a security boundary.

## Outstanding Concerns

- False confidence from a green suite: 75 passing tests sit on top of a broken primary safety feature because the linked-worktree test asserts a side effect (file written) instead of the actual contract (Git ignores the file). Safety/security guarantees should assert the effect.
- Once the exclude is fixed to target the common dir, concurrent queued requests for the same repo can read-then-append the shared info/exclude non-atomically; harmless duplicate lines, but worth a mutex or exclusive-create and a comment.
- resolveGitDir returns null silently on any read/parse error, skipping exclusion without a warning log — worth surfacing so operators can detect the accidental-commit risk.
- Optional text-content hardening (UTF-8/null-byte validation of downloaded bytes; accepting application/ndjson and .ndjson) as follow-up robustness items.
