## Executive Summary

This branch adds an optional iterative mode to the /plan command, decomposing planner output into a bounded task list and implementing each task individually with per-task diffing and planner verification before advancing. The core correctness problem is that the diff-per-task mechanism is broken: because the implementer is never instructed to commit changes, git rev-parse HEAD returns the same SHA on every task and every retry attempt, so git diff <preTaskSha> accumulates all prior-task changes rather than isolating the current task. The verifier therefore evaluates a growing, noisy diff that includes already-approved work, which defeats the stated purpose of the feature. Compounding this, git diff omits untracked files entirely, so newly created files are invisible to verification, and the iterative planner prompt drops the 'Do not edit files' guard present in the non-iterative path, permitting a tool-capable model to mutate the worktree during planning.

## Blocking Issues

- Cumulative diff accumulation makes per-task verification unreliable (src/services/iterativeTaskLoopService.ts): preTaskSha is captured via git rev-parse HEAD inside the while-loop on every task and every tweak attempt. Because the implementer never commits, HEAD never advances and every call returns the same SHA. git diff <sameSHA> therefore includes all uncommitted changes from every prior task and retry, not just the current task's changes. The verifier receives a growing, noisy diff that conflates already-approved work with the current task. The existing test mocks getHeadSha to return different SHAs per call, masking this bug in production.
- git diff excludes untracked files — newly created files are invisible to verification (src/services/gitWorkspaceService.ts): getDiffSinceRef uses git diff <baseRef>, which only covers changes to tracked files. Any file first created by the implementer (new source files, new tests, new config) is completely absent from the verifier's diff. The planner can approve a task while seeing none of its material output.
- Iterative planner prompt missing 'Do not edit files' guard (src/discord/bot.ts): The non-iterative planner prompt includes 'Do not edit files. Do not run the implementation.' The iterative planning prompt omits both instructions while still running with cwd: worktreePath. A tool-capable provider can therefore modify the worktree during the planning phase, with those mutations preceding all task-implementation cycles and attributed to no individual task.

## Non-Blocking Issues

- Dead MAX_TWEAKS_PER_TASK constant in bot.ts (src/discord/bot.ts): bot.ts defines const MAX_TWEAKS_PER_TASK = 3 but never references it — all iteration logic uses the separate copy in iterativeTaskLoopService.ts. Changing one copy silently diverges from the other.
- Unused imports: IterativeTaskOutput in bot.ts, getDiffSinceRef in botCommands.test.ts (src/discord/bot.ts): IterativeTaskOutput is imported at bot.ts:76 but never referenced. getDiffSinceRef is imported in botCommands.test.ts but the iterative tests mock runIterativeTaskLoop entirely so it is never called or asserted. Falling back to single-task implementation.' but then continues into the iterative loop with a single synthetic task. The user is misled about which code path runs. A redundant null-check immediately follows the message.

## Outstanding Concerns

- The design intent for commits is ambiguous: the implementer prompt only forbids committing a plan file, not committing implementation changes. If the intent is for each task's changes to remain uncommitted until the full plan completes (e.g., for atomic PR diffing), the fix cannot simply be 'commit between tasks' and must instead use stashing or git add --intent-to-add for a diff baseline. This design question should be resolved before prescribing a fix.
- The test suite mocks getHeadSha to return different SHAs per call, which validates correct behavior under an assumption (commits advance HEAD) that never holds in production without explicit commit steps. This gives false confidence that the per-task diff mechanism works and should be corrected regardless of which fix is chosen for the blocker.

**1. Diff accumulation across tasks — per-task verification is unreliable**

```js

The `$` anchor requires the closing ` ``` ` to be the very end of the string. ```js

```

The check rejects `**APPROVED**`, `APPROVED.`, `APPROVED\n...` (if there's stray whitespace between `\n` and `APPROVED` on the second line), or any markdown-wrapped variant. The planner is asked to verify a task given only:
- the task title/description,
- the implementer output,
- and the code diff.

It is *not* given the original prompt, the plan overview, or the outcomes of prior tasks (unless they failed). Without this context the planner may approve a locally correct change that is wrong for the full plan, or reject something that is correct when considered holistically.
