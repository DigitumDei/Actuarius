## Executive Summary

This branch adds an optional iterative plan mode to the /plan Discord command, decomposing requests into structured JSON tasks that are implemented, verified against the original request, and retried with feedback when rejected. Two blocking defects require resolution before merge: the verification approval parser at iterativeTaskLoopService.ts:56 uses /\bAPPROVED\b/iu, which matches the word 'APPROVED' anywhere on the first line — including inside 'NOT APPROVED — missing tests' — because the word boundary before 'A' does not suppress the preceding negation, causing the retry loop to silently accept explicit rejections as approvals; and per-task commit enforcement exists only as a prompt instruction with no programmatic gate, so uncommitted work passes verification via getDiffSinceRef (working-tree diff) but is invisible to getReviewDiff (committed-history diff), directly breaking the /review and /pr flows the bot directs users toward on iterative completion. Both defects have targeted, low-risk fixes that do not require architectural changes.

## Blocking Issues

- isApprovedVerification false positive on negated approval output (src/services/iterativeTaskLoopService.ts): iterativeTaskLoopService.ts:56 uses /\bAPPROVED\b/iu.test(firstLine). The word boundary \b matches between the space and 'A' in 'NOT APPROVED', so any verifier output that uses 'APPROVED' as a qualifier rather than a sole verdict — 'NOT APPROVED', 'partially APPROVED', 'APPROVED in part but…' — returns true and terminates the retry loop. The design intent is that the first line IS the approval token; the implementation tests whether the first line CONTAINS it. Fix: firstLine.toUpperCase().trimStart().startsWith('APPROVED') or /^APPROVED\b/iu. No test covers a negated-approval response.
- Per-task commit enforcement is absent; approved uncommitted work breaks downstream /review and /pr (src/services/iterativeTaskLoopService.ts): preTaskSha is captured once per task at line 74, outside the tweak while-loop. getDiffSinceRef (gitWorkspaceService.ts:520) runs git diff <sha>, which compares the SHA commit against the full working tree including staged and unstaged changes, so the verifier sees and can approve uncommitted work. getReviewDiff (gitWorkspaceService.ts:490) uses git diff remoteRef...HEAD, which only sees committed branch history. If the implementer does not commit, HEAD does not advance: subsequent tasks accumulate all prior uncommitted changes in the verifier's diff context, and downstream /review finds an empty committed diff while the bot has already printed 'Run /review, then /pr'. The success criteria explicitly require task commits; the only enforcement mechanism is a textual instruction in the implementer prompt.

## Non-Blocking Issues

- filter(Boolean) strips all blank-line separators from the implementer prompt (src/services/iterativeTaskLoopService.ts): Lines 91, 94, 97, 102 of iterativeTaskLoopService.ts are empty-string entries intended as section breaks between Repository, Original request, Plan overview, and Current task blocks. .filter(Boolean) at line 107 removes all of them, collapsing sections flush against each other. The verifier prompt at line 149 uses .join('\n') without filtering and is correctly spaced. This degrades every iterative implementer call silently; no test checks prompt line structure.
- stripMarkdownJsonFence ^-anchored regex fails on leading prose before the JSON fence (src/discord/bot.ts): bot.ts:207 applies the fence regex after .trim() but with a ^ anchor, requiring the opening fence at position zero. A common LLM output pattern — 'Here is the plan:\n```json\n{...}\n```' — does not match. JSON.parse then throws on the full text, parseIterativePlan returns null, and the bot silently falls back to a single monolithic task containing the entire planner output. The test suite only covers fence-only strings. Removing ^ or matching the first fenced block non-anchored is strictly more robust with no downside.
- MemPalace task summaries omit the collected per-task diff (src/discord/bot.ts): bot.ts:2931–2934 builds task summaries from implementerOutput and verificationOutput only. IterativeTaskOutput stores a diff field per task, but it is excluded from the drawer summary, weakening the stated goal of preserving useful per-task diffs and making post-run diagnosis of failed or max-tweak tasks harder.
- NUL-delimited untracked path .trim() can corrupt filenames with leading/trailing whitespace (src/services/gitWorkspaceService.ts): gitWorkspaceService.ts:526 applies .map((path) => path.trim()) after splitting on \0. POSIX permits leading/trailing whitespace in filenames; the trim is unnecessary and can alter valid paths. The .filter(Boolean) call that follows is still needed because git ls-files -z produces a trailing NUL, leaving a trailing empty string after split — only the .trim() should be removed.
- completedSummaries duplicated as verificationCompletedSummaries within the same loop body (src/services/iterativeTaskLoopService.ts): iterativeTaskLoopService.ts:81–83 and 122–124 perform an identical .map().join() over taskResults at the same point in execution. The two variables always hold the same value; one is redundant and adds maintenance surface.
- Exit-code detection in runGitNoIndexDiffWithOverflowFallback is string-fragile (src/services/gitWorkspaceService.ts): gitWorkspaceService.ts:178 detects git diff --no-index normal exit (exit 1 means differences found, not error) via (spawnError.message ?? '').includes('code 1'), relying on spawnCollect's internal error message format. spawnCollect exposes a numeric code property on the error object; checking spawnError.code === 1 would be more robust and consistent with how runGitDiffWithOverflowFallback checks spawnError.code === 'EMSGSIZE' at line 160.

## Missing Tests

- Negated approval regression: verifier output 'NOT APPROVED — missing error handling' must leave approved=false and increment tweakAttempts, not terminate the loop
- Commit enforcement loop tests: implementer leaves only working-tree changes (no commit), staged-but-uncommitted changes, and a properly committed task — expected behavior for each should match the stated requirement before this ships
- Integration test: iterative success leaves a non-empty committed diff visible to getReviewDiff, not only a working-tree diff
- stripMarkdownJsonFence with leading prose before the JSON fence: 'Here is the plan:\n```json\n{...}\n```' should parse correctly or the fallback should be explicit

## Disputed Issues

- Per-task error isolation: OpenCode classified missing try/catch inside the task loop as blocking, arguing transient provider errors on task N lose all prior work. Other reviewers and the critique rounds consider fail-fast intentional, supported by the 'propagates loop errors' test, and declined to treat it as a defect without an explicit resilience requirement.
- Missing return after parse failure in bot.ts:2876–2878: OpenCode raised this as blocking. Claude's critique and the consensus round noted the finding is self-refuted — the reviewer acknowledged no runtime crash occurs and the if/else fallback assigns all variables correctly. The concern is at most a structural fragility note, not a correctness defect.

## Outstanding Concerns

- The commit-enforcement fix requires a product decision that the reviews do not resolve: either (a) check that HEAD advanced after each implementer invocation and fail/retry if not, (b) commit programmatically before handing off to the verifier, or (c) redesign getReviewDiff to operate on the working tree rather than committed history and update the /review and /pr guidance accordingly. All three options are viable but have different implications for git history cleanliness and downstream workflow design.
- Silent feature degradation when stripMarkdownJsonFence fails on leading prose: the bot falls back to a single monolithic task with a user-visible warning but no explicit indication that iterative mode did not activate. Users who see 'could not parse iterative plan' may not understand the LLM ignored the formatting instruction, and the feature silently delivers no iterative benefit.
