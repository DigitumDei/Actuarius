## Executive Summary

This branch adds an iterative mode to /plan that decomposes requests into JSON tasks, runs each through an implementer/verifier loop with limited tweak retries, and captures per-task diffs and MemPalace summaries. It also tightens the APPROVED-parsing logic, moves /review to working-tree diffs, and blocks /pr on dirty worktrees. Two blocking issues prevent merging: the invalid-JSON fallback path passes uncapped raw planner text directly into every implementer and verifier prompt (bypassing the 8,000-char limit applied by the happy-path parser), and per-task diff isolation relies entirely on model compliance with a commit instruction rather than any code-enforced boundary — if an implementer leaves task N uncommitted, task N+1 captures the same HEAD SHA and its diff bleeds in task N's changes, directly violating the stated accuracy requirement. The /pr dirty-worktree gate is also entirely untested despite being an explicit success criterion.

## Blocking Issues

- Invalid-JSON fallback bypasses task description cap (src/discord/bot.ts): When plan JSON cannot be parsed, bot.ts falls back to a single task with description set to the raw planText with no truncateText call. The happy-path parser applies ITERATIVE_TASK_DESCRIPTION_LIMIT (8,000 chars), but this fallback skips it entirely, allowing arbitrarily large planner output to be injected verbatim into every implementer and verifier prompt across all MAX_TWEAKS_PER_TASK retry attempts.
- Per-task diff isolation is prompt-only, not code-enforced (src/services/iterativeTaskLoopService.ts): preTaskSha is captured once per outer task iteration before tweaks begin. If the implementer leaves task N's changes uncommitted, HEAD does not advance and task N+1's preTaskSha equals task N's, causing getDiffSinceRef to include task N's uncommitted changes in task N+1's diff. No post-implementation check verifies HEAD advanced or the worktree is clean. Additionally, the tweak prompt's 'amend or add commits' instruction can cause the implementer to rewrite earlier task commits, potentially making preTaskSha a dangling ref and aborting the loop. This directly violates the stated success criterion for accurate per-task diffs.
- No test coverage for /pr uncommitted-changes gate (src/discord/bot.ts): The hasUncommittedChanges check blocking /pr on dirty worktrees is an explicit success criterion with zero test coverage. The entire handlePr handler is untested in botCommands.test.ts — no test exercises the dirty-worktree rejection path, verifies pushBranch is not called, or confirms the ephemeral warning reply.

## Non-Blocking Issues

- diff_head stored SHA does not reflect working-tree scope of reviewed diff (src/services/adversarialReviewService.ts): getReviewDiff returns headSha as git rev-parse <branch> (committed tip only) while diffText includes staged, unstaged, and untracked working-tree changes. The /pr gate prevents pushing unreviewed uncommitted work, but the stored diff_head in the DB and displayed in reviews is semantically misleading — it cannot reproduce the full diff that was actually reviewed.
- Vanishing untracked file between ls-files and git diff --no-index crashes the loop (src/services/gitWorkspaceService.ts): getDiffSinceRef lists untracked files with ls-files then diffs each with git diff --no-index /dev/null <path>. If a file is deleted between the two calls, git exits with code 128 and empty stdout, which is not caught by the code-1 handler. The exception propagates as DIFF_FAILED, aborting the entire iterative loop. Low probability in single-worktree operation but a real unhandled crash path.
- getReviewDiff tests use fragile absolute-index mock sequencing (tests/gitWorkspaceService.test.ts): The test at gitWorkspaceService.test.ts sets up 9 sequential spawnCollect mocks and asserts via haveBeenNthCalledWith against absolute call indices. Any refactoring that reorders or adds git calls will silently shift indices, producing false-pass or false-fail results without any test failure indicating the mock ordering broke.

## Outstanding Concerns

- The 'amend or add commits' instruction in the tweak prompt (iterativeTaskLoopService.ts:106) could encourage the implementer to rewrite commits across task boundaries, not just the current task. If task-2's tweak amends the task-1 commit, preTaskSha becomes a dangling ref and getDiffSinceRef errors.
