## Executive Summary

This branch implements a `/revise` command that lets users revise an existing request thread's worktree by applying iterative changes guided by explicit findings or a prior review summary, integrating with the existing plan/implement loop. The dominant consensus finding is a two-part concurrency guard failure: `getLatestRequestWithWorkspaceByThreadId` filters on `worktree_path IS NOT NULL`, making active queued requests (which have no workspace row yet) invisible to the guard; simultaneously, a TOCTOU window between the active-status check and `createRequest` allows two concurrent `/revise` invocations to both pass and enqueue conflicting work on the same physical worktree. Since the `RequestExecutionQueue` is per-guild (not per-thread or per-worktree) with a default concurrency of 3, these races are realistic in production and must be resolved before merge.

## Blocking Issues

- Active-request guard misses queued requests without workspace attachment (src/discord/bot.ts): `getLatestRequestWithWorkspaceByThreadId` queries `WHERE worktree_path IS NOT NULL` (database.ts:501), so a thread follow-up or prior `/revise` that is queued but not yet running (and thus has null worktree_path) is invisible. `/revise` sees the older succeeded workspace row, passes the active-status check, and enqueues conflicting work against the same worktree. The fix requires querying active thread requests regardless of workspace attachment, or serializing the check-and-insert atomically.
- TOCTOU race: two concurrent `/revise` calls can both pass the guard (src/discord/bot.ts): The active-status guard fires synchronously at bot.ts:2539, but `deferReply` and `resolvePlanRoleModels` are awaited at bot.ts:2570–2572 before `createRequest` writes the revision row. Two concurrent invocations can both read the same `latestRequest` (succeeded, worktree=W1), both pass the guard, and both enqueue revision tasks targeting W1. With guild concurrency defaulting to 3, both can execute concurrently, causing interleaved git operations on the same checkout.

## Non-Blocking Issues

- Missing `excludePaths` for review artifacts in `getReviewDiff` (src/discord/bot.ts): `runReviseRequest` calls `getReviewDiff(input.worktreePath, { headRef: input.branchName })` without `excludePaths: ["docs/reviews/**"]`, while `/review` passes this exclusion at adversarialReviewService.ts:626. Files written by `/review` under `docs/reviews/` appear in the planner diff, adding noise and potentially producing spurious revision tasks.
- Admin-triggered `/revise` permanently transfers request ownership (src/discord/bot.ts): `createRequest` at bot.ts:2581 uses `interaction.user.id` (the invoking admin) rather than `latestRequest.user_id`. This new revision row becomes the latest workspace-bearing request for the thread. All subsequent permission checks for `/review`, `/pr`, `/delete`, and future `/revise` commands authorize against this admin-owned row, silently locking out the original requester unless they also hold `Manage Server`.
- "Revision started" message sent before work actually begins (src/discord/bot.ts): The public thread message at bot.ts:2622 says "Revision started" immediately after enqueueing, while the ephemeral reply correctly says "Revision queued." Thread watchers see a contradictory message for work that may not start for minutes.

## Missing Tests

- Two near-simultaneous `/revise` invocations on the same thread — only one revision request should be created and enqueued

## Disputed Issues

- Whether thread follow-up messages reuse the existing worktree (W1) or allocate a new path — Claude asserted they create new worktrees; Codex and OpenCode cite bot.ts:570-571, bot.ts:643, and bot.ts:3479-3481 showing `existingWorktreePath` being passed through and reused. If the reuse path is confirmed, the follow-up + revise scenario broadens the blast radius of the blocking guard gap beyond the two-concurrent-revise case.
- Severity of the missing `excludePaths` — OpenCode classified it blocking; Codex and Claude classified it non-blocking. The review-artifact pollution is real but produces spurious tasks rather than data loss or worktree corruption; non-blocking is the consensus position.
- `findLatestReviewSummary` branch-name coupling across ancestry — OpenCode raised this as a strong concern; Claude and Codex found it speculative since `/revise` currently reuses the source branch. Not a current defect.

## Outstanding Concerns

- No concrete serialization mechanism was proposed or evaluated: a per-worktree mutex, per-thread queue, or DB-level advisory lock is needed to make the guard robust. The fix of "query unfiltered active requests" addresses the null-workspace blind spot but does not close the TOCTOU window for concurrent `/revise` calls without also serializing the check-and-insert.
- The `tasks` return value from `runParsedIterativeImplementation` may be dead code at the `runPlanRequest` call site after refactoring — `overview` is used in the MemPalace drawer, but `tasks` appears unreferenced after destructuring. Not confirmed without reading the full post-refactor body.
- A failed mid-revision leaves the shared worktree in an indeterminate state, and there is no reset or cleanup mechanism before the next `/revise` attempt on the same thread. Unlike `runPlanRequest`, which has `cleanupFailedWorktree`, the revise path deliberately preserves the worktree but offers no way to restore it to a known-good state.
