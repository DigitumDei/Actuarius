## Executive Summary

The branch adds a `/revise` slash command that enqueues a new revision request linked to the original, runs a planning step, and drives an iterative implementation loop on the existing worktree. Two blocking issues prevent merging: the revision DB row and workspace attachment are created before `deferReply` and role resolution are awaited in `handleRevise`, so any setup failure leaves a permanently-queued record that blocks all future `/revise`, `/review`, and `/pr` operations on the thread; and `revision_of_request_id` is correctly inserted via `RETURNING *` but silently stripped by Zod before any typed caller can observe it, a data-layer correctness gap that will cause silent wrong results as soon as the field is consumed. The overall control flow, worktree lifecycle, and happy-path coverage are structurally sound, but both issues require remediation before the branch can merge.

## Blocking Issues

- Orphaned queued revision request on pre-enqueue failure (src/discord/bot.ts): `createRequest` and `updateRequestWorkspace` execute at lines ~2569–2579, creating a `queued` record with workspace attached, before `deferReply` and `resolvePlanRoleModels` are awaited. Neither call is guarded. If either throws, the revision row remains `queued` with a workspace path, becoming the 'latest' workspace request for the thread and permanently blocking subsequent `/revise`, `/review`, and `/pr` operations. The outer `handleCommand` catch logs and replies but does not mark the revision row failed. Fix by moving `createRequest`/`updateRequestWorkspace` into a guarded path that runs only after setup succeeds, or by wrapping setup calls and marking the record failed on any exception.
- `revision_of_request_id` missing from `requestRowRawSchema` and `RequestRow` (src/db/schemas.ts): The column is added via migration and correctly sent in the `INSERT ... RETURNING *` statement, but `requestRowRawSchema` (src/db/schemas.ts) and `RequestRow` (src/db/types.ts) omit it. Zod's default strip mode silently discards the field from every `createRequest` return value and every subsequent row retrieval. The field is not read back by current code, so no runtime crash occurs today, but the stored linkage is invisible to the application layer and any future caller accessing `row.revision_of_request_id` gets a TypeScript error. This was flagged as blocking by two of three reviewers and as 'must be fixed' by all three; the same commit that adds the column must update both the schema and the interface.

## Non-Blocking Issues

- Dead `requestId` parameter in `runParsedIterativeImplementation` (src/discord/bot.ts): The method signature accepts `requestId: number` but the body never references it — it is not passed to the task loop, used in message sends, or included in the return value. Both call sites pass it, suggesting either incomplete refactoring or copy-paste drift. Should be removed or wired up.
- Review-summary fallback lookup fragile across revision chains (src/discord/bot.ts): `getLatestCompletedReviewRunForBranch(input.sourceRequestId, branchName)` queries `review_runs WHERE request_id = ?`. After a first revision completes, `latestRequest` becomes the revision request (e.g., #42), but any completed review is recorded against the original (#41). A second `/revise` with omitted findings finds no review and silently falls back to no context. The lookup should walk `revision_of_request_id` back to the original request or query by branch/thread rather than by request ID.
- "Revision started" user message sent before `enqueue()` is called (src/discord/bot.ts): `interaction.channel!.send("Revision started...")` fires before `this.requestQueue.enqueue(...)`. If `enqueue` throws, the user sees a start message but no job runs. In practice `RequestExecutionQueue.enqueue` is a pure in-memory push that cannot throw, so the risk window is currently zero — but the ordering should be inverted for clarity and defensive correctness.
- MemPalace drawer uses "Latest Review Summary" heading when no review exists (src/discord/bot.ts): When both `input.findings` and the review-summary lookup are null, the drawer records the heading `### Latest Review Summary` followed by `(none)`. A reader of the palace history sees a heading that implies a review was found. The heading should be conditional or qualify that no completed review was found.
- Help text describes `/revise` as a "plan thread" command (src/discord/messageTemplates.ts): The help text says "Re-run planner-verified implementation on the current plan thread" but the command works on any tracked request thread, not only plan threads. The slash command description in `commands.ts` is more accurate; the help template should be aligned.
- Hardcoded `tmpdir()` path in missing-worktree test (tests/botCommands.test.ts): `join(tmpdir(), "actuarius-revise-missing-worktree")` is used as the fake worktree path. If that path happens to exist (prior crash, CI artifact, parallel test), the test bypasses the `existsSync` guard and fails for an unrelated reason. Use `mkdtemp` and immediately remove the directory, or mock `existsSync` directly.

## Missing Tests

- Whitespace-only `findings` (e.g., `"   "`) treated identically to null — explicitly required by the success criteria, implementation is correct but untested
- Setup failure between `createRequest`/`updateRequestWorkspace` and `enqueue` — confirms that the revision row is marked failed rather than left permanently `queued`
- Repeated `/revise` with omitted `findings` after a prior revision exists — confirms that review-summary fallback still finds the correct review attached to the original request
- `revision_of_request_id` round-trips correctly through `createRequest` and request retrieval APIs (DB integration test)
- `getRepoByChannelId` returning null — handler replies with an error before any `createRequest` is called
- Thread unavailable (deleted or unfetchable) during `runReviseRequest` execution — confirms `markFailed` is called and the function returns cleanly

## Disputed Issues

- `markFailed` double-fail on synchronous DB error: OpenCode classified as blocking; Claude and Codex argue the same pattern exists throughout the bot, SQLite DatabaseSync errors are deterministic rather than transient, and the error propagates and is logged rather than causing silent data corruption — not elevated to blocking by consensus.
- `threadChannel.send` type narrowness in `runParsedIterativeImplementation`: OpenCode raised as non-blocking; others dismissed as speculative — no current caller needs embeds or attachments via this path, so the narrow contract is not an actionable defect today.

## Outstanding Concerns

- The review-lookup-by-`sourceRequestId` design is architecturally fragile beyond the repeated-revise scenario: the same pattern in `handlePr` also passes `latestRequest.id`, meaning the entire review/PR/revise flow assumes the worktree-owning request is the same record that has the review. This assumption breaks whenever a user re-plans or re-asks on an existing thread without running a new `/review`. A branch-scoped or thread-scoped review lookup would be more robust, but fixing this is a larger design change beyond the scope of this PR.
