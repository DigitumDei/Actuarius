## Executive Summary

This branch adds a `/revise` command that lets users iterate on an existing request/worktree using either explicit findings or the latest review summary, reusing the extracted `runParsedIterativeImplementation` path shared with `/plan`. Two structural correctness defects block merging: the command never writes an active status to the DB before enqueuing, so a second concurrent `/revise` (or `/review`, `/pr`, `/delete`) passes the guard and races against the pending job on the same worktree; and `runReviseRequest` updates the *original* request row to `running`/`succeeded`/`failed`, which can retroactively corrupt a clean historical record and conflates a distinct execution event with the original one. The refactor of `runParsedIterativeImplementation` itself is clean and behaviorally equivalent, but the revision-specific orchestration layer is not safe to ship as-is.

## Blocking Issues

- Pre-queue status race: request row not marked active before enqueue (src/discord/bot.ts): handleRevise checks isActiveRequestStatus then enqueues without writing any state to the DB. The status write to 'running' only happens inside the queued closure. During the gap, a second /revise, /review, /pr, or /delete call reads the still-'succeeded' row, passes the guard, and enqueues a second concurrent job against the same worktree. Contrast with /plan and /ask, which insert a new request row with status 'queued' before calling enqueue, making the active state immediately visible.
- Revision overwrites original request's terminal DB status (src/discord/bot.ts): runReviseRequest calls updateRequestStatus(input.requestId, 'running') on the original request ID, then updates it to 'succeeded' or 'failed'. A failed revision retroactively marks a previously successful request as 'failed', destroying audit history. There is no way to distinguish the original completion from a revision attempt in the requests table. A revision is a distinct execution event and should produce a new row (potentially with a revision_of FK) rather than mutating the original record.

## Non-Blocking Issues

- Diff computed against local branch tip instead of merge-base (src/discord/bot.ts): runReviseRequest passes defaultBranch.branchName to getDiffSinceRef, while the review diff path computes merge-base(defaultBranch.remoteRef, headRef) first. If the local branch lags origin, the two-dot diff includes upstream commits unrelated to the branch under revision, giving the planner misleading context.
- MemPalace drawer omits the key revision inputs (src/discord/bot.ts): The drawer records plan text, overview, and task results but not input.findings, the resolved reviewSummary, or the branch diff. The most important inputs to the revision—what drove it—are not preserved, weakening later diagnosis.
- resolvePlanRoleModels awaited before interaction.deferReply (src/discord/bot.ts): The async role resolution runs before the 3-second Discord interaction acknowledgment window closes. /plan defers first and resolves roles afterward. A latency spike in role resolution under /revise can cause an expired token error before the reply is sent.
- Command description in commands.ts is too narrow (src/discord/commands.ts): The registered description says 'Re-run planner-verified implementation on the current plan thread', but handleRevise accepts any tracked request thread including /ask threads. The description should reflect the actual scope.
- TOCTOU on existsSync worktree check (src/discord/bot.ts): The filesystem guard in handleRevise runs before enqueue; runReviseRequest runs later via the queue. A worktree deleted between the two points produces a confusing internal git error rather than the clear guard message. The catch block prevents a crash but the UX is degraded.
- Test temp directories are never cleaned up (tests/botCommands.test.ts): The revise test suite creates real mkdtemp directories with no afterEach cleanup, accumulating temp dirs across test runs.

## Missing Tests

- No test that /revise is rejected (or at minimum warned) when both explicit findings and latest review summary are absent
- No test demonstrating that a second concurrent /revise on the same thread is blocked while the first is queued
- No test for non-owner, non-admin user attempting /revise (ownership rejection path has zero coverage)
- No test where existsSync returns false for the worktree path in handleRevise
- No test where the planner returns an empty or whitespace-only response, exercising the markFailed early-return
- No test for detectDefaultBranch or getDiffSinceRef throwing (broken worktree / git failure path)
- No test where both input.findings is provided and a review summary exists (confirming summary is ignored when findings are explicit)

## Disputed Issues

- Whether proceeding without any findings and without a completed review summary is a blocking defect or a product/UX design question: Codex treated it as blocking; Claude and the consensus judge downgraded it to non-blocking, noting the planner still receives the original request and diff and can produce a valid revision.

## Outstanding Concerns

- The root-cause design decision—reusing the original requestId/row rather than inserting a new requests row for each revision—is the single source of both blocking issues. All three reviewers independently converged on inserting a new row (potentially with a revision_of FK) as the correct fix. The current approach trades correctness guarantees for brevity and will remain fragile even after a narrow status-write patch unless the data model is changed.

### Claude (claude / claude-sonnet-4-6)

```text
**Blocking Issues**

**1. Race condition: no DB write before enqueue means two concurrent `/revise` calls on the same thread can both execute.**
`handleRevise` checks `isActiveRequestStatus(latestRequest.status)` and immediately enqueues—no DB row is created or updated to mark the request as active. The status write (`"running"`) only happens inside the queued job. With `maxConcurrencyPerGuild = 3` and the gap between check and execution, a second `/revise` on the same thread can pass the status check while the first is queued, and both land in the queue concurrently. Both jobs call `updateRequestStatus(requestId, "running")` on the same row, and both work on the same `worktreePath` string simultaneously. Compare to `/plan` and `/ask`, which insert a new `requests` row before queuing, making the status immediately visible via that row. `/revise` has no equivalent locking step.

**2. The revision overwrites the original request's terminal DB status.**
`runReviseRequest` calls `this.db.updateRequestStatus(input.requestId, "running")` on the original request ID. If the revision fails, the original `"succeeded"` request becomes `"failed"` in the DB. There is no new `requests` row for the revision. This means: (a) a successful historical request can be retroactively marked failed by a revision attempt; (b) there is no way to distinguish the original completion from a revision in the DB; (c) the "failed" status from the revision will block a future `/revise` check—wait, no, `isActiveRequestStatus("failed")` returns `false`, so it still allows another attempt. But the corrupted history is real. The intent may be to reuse the same row as a "continuation," but this is not stated in the code or comments and conflicts with the historical semantics of the `requests` table.

---

**Non-Blocking Issues**

**3. `resolvePlanRoleModels` is awaited before `interaction.deferReply`.**
All the sync checks plus an async DB/config call happen before the 3-second interaction acknowledgment window. For other commands this is the same pattern, so it's unlikely to be new, but it is still a correctness footgun under any latency spike.

**4. Public "Revision started." message fires before the job is actually in the queue.**
`interaction.channel!.send("Revision started.")` is followed by `this.requestQueue.enqueue(...)`. If `enqueue` were to throw (e.g., queue saturated with a bounded capacity), the message would have already been sent. Existing commands use this same pattern, but it is a cosmetic inaccuracy.

**5. `stage` variable in `runReviseRequest` is not updated after `runParsedIterativeImplementation` is called.**
If `runParsedIterativeImplementation` throws internally (e.g., from `runIterativeTaskLoop`), the error message reads "Revision failed during iterative-loop"—which is accurate—but any exception thrown *after* the `tasks/overview/taskResults` destructure (e.g., a hypothetical DB write failure in the success block) would also blame "iterative-loop". Low impact but potentially misleading diagnostics.

---

**Missing Tests**

- **Ownership rejection**: No test for a non-owner, non-admin user attempting `/revise`. The `isOwner && canManageGuild` path has zero coverage.
- **Worktree not on filesystem**: `existsSync` check is implemented but not covered.
- **Empty planner output**: The `if (!planText.trim())` early return with `markFailed()` is not exercised.
- **`getLatestCompletedReviewRunForBranch` returning non-null with findings also provided**: Edge case where both `input.findings` is set and a review summary exists—the summary should be ignored. Not explicitly tested.
- **Concurrent `/revise` invocations**: No test demonstrates the race described in blocking issue #1.

---

**Strong Concerns**

The decision to reuse the original `requestId` (and thus the original `requests` row) rather than inserting a new one is the root cause of both blocking issues. A revision is a distinct execution event. Inserting a new row with a `parent_request_id` or `revision_of` foreign key would solve the race (new row → status immediately visible), preserve audit history (original status unmodified), and allow `/revise` itself to show up in request listings. The current design achieves brevity at the cost of correctness guarantees.

The `runParsedIterativeImplementation` refactor is clean and the extraction is correct. The `plan`-path refactoring (replacing inlined logic with the new method) looks functionally equivalent to the original. No regressions observed there.

---

**Confidence**

Medium-high on the race condition and status-overwrite issues; both are demonstrable from the code without relying on runtime conditions. High confidence that the three missing test paths (ownership, filesystem check, empty planner) are genuinely absent from the diff.
```
